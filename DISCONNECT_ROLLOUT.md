# Guarded disconnect rollout

`DISCONNECT_PAUSED=true` (case-insensitive, surrounding whitespace ignored) makes the authenticated subcontractor connection-removal API return 503 without changing connections, join generations, or QR codes. `/api/sub/my` exposes only `disconnect_available`, and the dashboard disables removal when this is false or absent. Unset or `false` restores normal removal. This is not maintenance mode: login, uploads, joining, and connection QR operations remain available. Existing connections remain active while removal is paused. Issued download links and already downloaded files are unaffected.

## Deployment safety boundary

The guard only protects requests that reach code implementing it with the variable enabled. A legacy instance cannot be made safe by setting this variable on a new instance, and an old client may still show a remove button; the server guard is authoritative. During any overlap of legacy join behavior and active disconnect behavior, the overlap remains unsafe. Before allowing removal on any new instance, ensure all instances capable of legacy joins have fully drained, including in-flight requests, background traffic and alternative routes. Ensure all relevant traffic reaches guarded instances configured with the pause throughout the overlap. If that cannot be guaranteed, use an independently verified ingress-level block on the DELETE disconnect route or avoid the unsafe overlap; this feature alone cannot guard legacy instances. Verify real deployment routing and health independently; no production change is made by this documentation.

After the old instances and their in-flight requests have drained and the new implementation is verified, removal can be re-enabled by clearing the variable or setting it to `false` on **all** instances via the approved deployment process. During rollout, mixed flag values can cause inconsistent UI and 503 responses, so coordinate the setting across instances. No database migration is introduced by this guard. Existing legacy JWTs continue to work in the portal but cannot create or consume join intents; users must explicitly sign out and sign in again for invitation joining. Tokens generated by the current signer include a unique JWT ID. If sign-in reaches an older instance that still issues legacy tokens, signing in again may not resolve the prompt until that instance drains. The stored intent session binding remains the SHA-256 hash of the existing Authorization header, not the token or its JWT ID.

## Isolated checks

From the repository root: `node --experimental-strip-types --test server/test/guarded-rollout.test.ts`, `python3 client/tests/test_sub_disconnect.py`, and `python3 client/tests/test_session_consistency.py`; run `npm run build`. These tests use an isolated temporary SQLite database and mocked browser endpoints; they do not verify Railway propagation or PostgreSQL concurrency.
