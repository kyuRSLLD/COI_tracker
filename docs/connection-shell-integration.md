# Connection-only shell integration — local build, not deployment approval

This additive integration is **not deployed and not ready for exposure**. It does not modify the Dockerfile, Railway settings, package scripts, legacy server, existing V2 components, pilot factory or entry. No database migrations, provisioning, AWS requests or cloud operations were performed. The new `server/src/connection-shell-entry.ts` imports the existing real `createPilot`, then wraps its Express app; no synthetic runtime dependencies or mock fallback are used. `server/test/connection-pilot/browser-fixture.ts` is strictly test-only and is never imported by the runtime entry.

## What it serves and what it does not

The new Vite entry mounts `<V2Shell connectionOnly />` and builds only its own HTML, JS and CSS under `client/connection-pilot/dist/`, an ignored generated directory. `publicDir: false` prevents copying legacy static files. The wrapper snapshots the index and only syntactically valid Vite-hashed JS/CSS assets from that output at startup, checks size and rejects symlinks or unexpected asset files. Only `/` and exact generated `/assets/<hash>` URLs are served; missing files, index aliases, queries, encodings, traversal and other paths are not rewritten to the shell. Requests under `/api/v2/` and `/healthz` are delegated to `createPilot`, whose own stricter exact allowlist remains authoritative. Legacy, owner, file and metadata API routes remain unavailable. `/healthz` is liveness **only**, including while the DB is unavailable; it is not readiness.

The connection-only mode hides metadata, files and related UI/requests; both client transport and pilot route allowlists independently reject those APIs. Existing `V2Shell` imports the broader shared components, so dormant file/metadata implementation code and strings can remain in the bundle; this change does **not** claim that code has been tree-shaken out. There is no runtime access to those capabilities through this composition. The QR uses a locally rendered SVG; camera access is permitted for this origin, requires browser support, permission and a secure context (or localhost), and has a manual fallback.

The document response has `default-src 'none'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'self'`, restrictive frame/object/base/form/worker directives, `Referrer-Policy: no-referrer`, `nosniff`, no-store, and `Permissions-Policy: camera=(self)` with microphone/geolocation disabled. The original `createPilot` emits its own more restrictive API response policies. No remote scripts or Vite development runtime are loaded by the built page. `script-src 'self'` trusts *all* same-origin scripts; a dedicated origin, immutable reviewed build output and elimination of any alternate handler or service worker on that origin are prerequisites, not guaranteed by this code. Browser extensions and compromised same-origin code are outside the guarantees.

The browser entry installs a fixed-method, literal-path transport allowlist, same-origin only, which forces credentials omitted, rejects redirects and queries, uses a 10-second abort, allows at most eight concurrent requests, and bounds request bodies to 8 KiB and buffered responses to 256 KiB. No automatic retries occur; a timeout can mean a write committed but its result is unknown. Large legitimate lists can exceed the response cap and appear unavailable; capacity and pagination require review. Tokens and QR capabilities remain transient in memory, not URLs, browser storage or console logs; API requests use a bearer header, `credentials: 'omit'` and `no-referrer`. The wrapper removes any incoming cookie before delegation and prevents `Set-Cookie` responses. A browser can nevertheless attach pre-existing origin cookies to normal document/asset navigation before the server strips them; use a clean, exclusive origin and remove old cookies/service workers before exposure. This is not a guarantee against secrets being logged by ingress, proxies, database drivers, browser extensions, or third-party instrumentation.

The server bounds headers to 8 KiB, `Content-Length` to 8 KiB, timeouts (header 10 s, request/inactivity 15 s, keepalive 5 s), and connections to 100 per process. The existing API parsers and pilot limits remain in force; chunked requests and aggregate cross-replica traffic also require ingress controls. Existing pilot limitations and direct-socket peer attribution remain: behind a proxy the peer may not be the end user, and fixed-window abuse limits can deny legitimate traffic. A dedicated, authenticated, TLS-terminating ingress with reviewed trusted client IP policy, body/connection/concurrency limits, direct-origin prevention and secret-safe observability is still required. Never log headers, bodies, token-bearing URLs, codes, credentials, raw addresses or provider errors.

## Reproduce locally

From `/home/ubuntu/coi-secure-v2`, with the existing locked workspace dependencies installed and Node 22+, build only this UI:

```sh
./node_modules/.bin/vite build --config client/connection-pilot/vite.config.ts
```

Do not use the legacy root `npm run build` or deployment commands for this entry. Build output is ignored and must be rebuilt; run the build in a trusted clean checkout, keep output immutable, and start the source entry only with the same relative tree layout. No secrets belong in this build. No deploy/start command has been inserted into any existing configuration. The source entry expects `PORT` and the strict runtime pilot settings in `docs/pilot-bootstrap.md`. It creates real PostgreSQL and SES clients, probes only the limiter schema/shared key before listening, then listens; the probe is not a migration and is not comprehensive readiness. **Do not run against real infrastructure without separate authorization and all prerequisites below.**

The following tests use synthetic keys, loopback-only listeners and, for the actual `createPilot`, an intentionally unreachable localhost database on port 1; no SES call is made. The browser fixture is synthetic, not an end-to-end test of the actual auth/connection DB services. The browser command requires Python Playwright and `/usr/bin/chromium`:

```sh
./node_modules/.bin/tsc --noEmit --target ES2022 --lib ES2022,DOM,DOM.Iterable --jsx react-jsx --module ESNext --moduleResolution Bundler --strict --skipLibCheck --allowSyntheticDefaultImports client/connection-pilot/main.tsx client/connection-pilot/network.ts
./node_modules/.bin/tsc --noEmit --target ES2022 --module NodeNext --moduleResolution NodeNext --strict --esModuleInterop --skipLibCheck --allowImportingTsExtensions server/src/connection-shell-entry.ts server/src/connection-shell-wrapper.ts server/test/connection-pilot/wrapper.test.ts server/test/connection-pilot/browser-fixture.ts
env -u NODE_OPTIONS node --experimental-strip-types --test server/test/connection-pilot/wrapper.test.ts
python3 server/test/connection-pilot/browser-test.py
```

Observed locally: Vite production build succeeded (1,588 modules); both targeted type-check commands passed; HTTP tests **3 passed, 0 failed**; browser test passed for synthetic login, consent, QR, manual and simulated camera redemption/cleanup, restrictive CSP, no browser storage or cookies, same-origin requests and bounded transport (oversize, concurrency and stalled response). Camera hardware and real QR decoding were not tested. The browser test intercepts media devices only; ordinary synthetic API requests go through the actual wrapper and local fixture. The HTTP test uses the real factory but only proves liveness, fail-closed DB unavailability, and surface isolation—not successful authentication or connection transactions.

## Before any deployment decision

Complete an independent security review of the entire changing V2/pilot code and this composition; isolated end-to-end tests with a real disposable DB and synthetic messaging for registration, role isolation, login, QR, consent, replay, revoke, concurrency and failure scenarios; a separately reviewed fresh database schema, least privilege, TLS and no untrusted writers; a real separately authorized SES/IAM/mailbox test; dedicated HTTPS origin and ingress/abuse/cookie/service-worker controls; correct secret management and safe observability; asset supply-chain and reproducible-build review; real device/camera compatibility; capacity, rate limits, response-size and timeout assessment; readiness and operational monitoring, retention, backup/restore and incident/rotation/rollback plans; and an explicit reviewed build/start/cutover configuration that cannot start or expose legacy routes. See `docs/pilot-bootstrap.md` for pilot-specific settings and unresolved blockers. None of these prerequisites are asserted to be complete here.
