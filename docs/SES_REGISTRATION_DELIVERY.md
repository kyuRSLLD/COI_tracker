# SES v2 registration delivery (disconnected)

This is an isolated adapter, not an enabled registration feature. It implements the `RegistrationDelivery` shape; the local structural type should be reconciled with the canonical registration type before any separately reviewed release integration. No live application entry point imports or starts this adapter. The synthetic-only harness composes it with the registration router only when an explicit mock transport is provided; that path does not create an SES SDK client. See `secure-v2-synthetic-composition.md`. `createSesRegistrationDelivery({ region, fromEmailAddress })` must be called only by trusted server composition and passed as the registration `delivery` dependency, never sourced from a request. The optional second argument is a test-only mock seam; do not expose it to untrusted input. All configuration is mandatory except `timeoutMs` (default 8 seconds, allowed 100–15,000 ms). Bad or missing values fail closed. Do not invent or hard-code deployment values.

The registration module generates 32 random bytes using a CSPRNG and sends their canonical 43-character base64url representation. The adapter checks the representation, not randomness or one-time use: upstream must generate a fresh cryptographically random 256-bit token, securely store only its hash, enforce expiry, consume it atomically once, and apply shared/IP/email rate limits. This adapter must not be used with user-selected or predictable tokens. It sends one plain-text email with the exact code, no URL, HTML, templates, tracking image or link. It disables both SES click/open tracking explicitly per message, even if an account or identity default enables them. No message IDs, contents, addresses, codes, credentials, SDK exceptions, or provider metadata are logged here; all failures surface as the same generic error, without a cause. Keep HTTP logs, APM, tracing, outbound SDK middleware, proxies, queues, exception reporters and request bodies similarly redacted; email itself and the provider necessarily see the code and address. Privacy cannot be guaranteed against a compromised mailbox or server infrastructure.

The adapter uses an explicitly configured AWS region and sender and the Node.js AWS SDK default credential provider chain (prefer temporary credentials through a workload IAM role). It does not accept secrets, endpoint overrides, or client-supplied senders. The SDK's configured endpoint URL environment overrides are disabled, but deployment must also prevent untrusted proxy, TLS, region and credential-provider configuration. It uses one SDK attempt, an abort signal and a bounded caller deadline. A timeout does **not** prove SES did not accept a message: an in-flight request may have reached SES and credential resolution may not itself be cancellable. The upstream registration implementation must leave an ambiguous/failed send unarmed and refuse confirmation, as in the referenced registration module; a recipient might receive an unusable code. Do not retry the same challenge automatically. A `MessageId` means SES accepted the send, **not** that it delivered it, that the mailbox received it, or that a person controls it. Only successful redemption proves code access.

## Before release (no account or deployment has been configured here)

1. Obtain the AWS account, SES-supported region, and exact sender identity from the operator. Verify the email or domain identity in **that region**; for a domain publish the SES-provided DKIM DNS records and wait for verification. Configure domain authentication and DNS as appropriate, including DKIM, SPF/custom MAIL FROM and DMARC; check sender/domain alignment with the mail administrator. Domain identities may permit straightforward inherited sending, but AWS notes advanced settings may require an explicitly verified email identity. This adapter cannot establish the sender's verification status locally; SES rejects an unauthorized/unverified identity. See [AWS identity verification](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html).
2. Request SES production access for the region before sending to arbitrary recipients. In the SES sandbox, recipients must be verified identities or the mailbox simulator, with a quota of 200 messages per rolling 24 hours and one message per second. Production remains subject to region-specific quotas, rolling recipient counts, throttling, suppression, reputation and bounce/complaint handling. Plan rate limiting, quota monitoring and operational response. [Sandbox](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html); [quotas](https://docs.aws.amazon.com/ses/latest/dg/manage-sending-quotas.html).
3. Grant the workload least-privilege `ses:SendEmail` for the intended identity and any applicable default configuration set. The per-message tracking override also requires `ses:ApplyTrackingConfigurationOverrides` on `*`; use AWS's condition keys to permit only both `DISABLED` values. Validate effective policy, region support, identity defaults and security controls with the operator. No IAM changes are performed by this work. [AWS tracking override and IAM](https://docs.aws.amazon.com/ses/latest/dg/configuration-overrides.html).
4. Review any identity-level default configuration set, archives, event destinations, monitoring and retention. Overrides only suppress SES open/click tracking, not all message-processing, archiving, external mail security, delivery/bounce/complaint events, recipient-side tracking or logging. Ensure none captures message contents, verification codes or sensitive request data. Adopt privacy-preserving aggregated alerts and handle bounces/complaints without exposing tokens.
5. Integrate only after security review of the registration service, its atomic challenge lifecycle, generic HTTP responses, rate limiting, expiration, UI code-entry flow, TLS, account-enumeration resistance and no-store/redaction controls. Review deployed SDK and transitive dependencies and support for the tracking override in the selected region. Test with mock transport and a disposable database; any future real SES test requires explicit authorization and approved recipients. A storage bucket is not used by this adapter.

The authoritative [SES v2 SendEmail API](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html) defines the `Simple` message and acceptance response. The [AWS SDK JavaScript v3 credential guidance](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/migrate-credential-providers.html) describes its default provider chain.

## Local test

With Node 22 supporting `--experimental-strip-types` and dependencies installed, from the repository root run `node --experimental-strip-types --test server/test/ses-registration-delivery.test.ts`. Tests inject a mocked SES transport; an additional SDK serialization test uses dummy credentials and a strictly in-memory HTTP handler. No test calls AWS or sends messages.
