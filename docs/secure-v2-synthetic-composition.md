# Secure V2 synthetic composition — test only, disconnected

`server/src/secure-v2-synthetic.ts` composes the actual V2 auth, GC owner, consent/connections, and private certificate routers into the standalone `createSecureV2App`. It is **not a production entry point**; it is not imported from the live app or startup, does not listen, run migrations, seed data, load production configuration, or create a real S3 client. Nothing here changes maintenance or legacy routes. Never deploy or mount this harness.

The factory requires `NODE_ENV=test`, a `pg.Pool` whose explicit URL is `127.0.0.1:port/secure_v2_test_*` without URL options, and server-owned synthetic RSA config. Those checks are guardrails only: neither a name nor an environment variable proves disposability. Trusted test callbacks/transports are executable code; the factory cannot prove that a supplied callback is safe or that a supplied transport is genuinely a mock. Use **only** the supplied disposable-cluster runner on a trusted isolated computer, with synthetic data, keys, policies and in-memory object storage. Do not connect this to real/shared databases, real identities, real S3, or a public listener.

## Identity, route and body boundaries

- Public auth is `/api/v2/auth`; owner routes are `/api/v2/gc`; connections are `/api/v2/connections`; files are `/api/v2/certificates`. The outer factory denies legacy/static paths, ambiguous paths and duplicate/malformed Authorization headers, returns generic errors, and sets no-store/security headers.
- The outer protected gate calls the actual `requireAuth`, which verifies the RS256 credential and checks the session/account/current role in PostgreSQL. It rejects any pre-existing `req.securePrincipal` and deliberately does **not** create one. Each enabled router then calls the adapter, which runs `requireAuth` again, reads only the freshly established `res.locals.authV2`, freezes a copy, and defines a non-writable/non-configurable request principal. A private WeakMap permits repeated adapter calls only after another successful verification and only when subject, role and credential are unchanged; foreign properties are rejected. Neither client JSON, query parameters, spoofed identity headers, nor JWT role claims establish identity.
- This ordering matters: the certificate router deletes a prior `securePrincipal` before its own verifier. Pinning at the outer gate would make that deletion throw. The outer gate supplies no such property; the certificate router clears any prior configurable value and the adapter verifies and pins a new value. The outer gate rejects any pre-existing property outright, including non-configurable properties. Do not rearrange, mount behind an identity-pinning middleware, or reuse the adapter with an unreviewed verifier. `res.locals.authV2` is cleared and rebuilt by every real `requireAuth` call.
- The factory's default remains a 64 KiB JSON parser. This concrete composition sets `routersOwnBodyParsing`, so actual router limits work: auth 8 KiB, owner 64 KiB, connections 4 KiB. The certificate router receives the unconsumed raw request; it validates MIME, length, encoding, and a 10 MiB actual byte limit. JSON/multipart are not valid file uploads. Parser/status conventions vary by router but bodies remain generic. The real proxy must independently enforce body, decompression, header, timeout and concurrency limits.
- An explicitly supplied test rate callback is invoked before auth routes and, on protected routes, before the outer verifier and again with the verified subject. The consent router also invokes its own preauth/principal phases. Missing limiter fails closed with 503; non-true is 429; errors/timeouts are 503. The callback receives a TCP peer address, not a trusted proxy-derived client address, and no request body or credential. It is **not** a real distributed limiter or a complete login account-abuse control. Double charging the protected and connections-router scopes is intentional in this harness; real policy budgets need a separately reviewed design. Callback timeouts do not cancel underlying work.
- Consent routes are **disabled by default**, enabled only by the unsafe synthetic-only option. The consent service now independently verifies strict JWTs and transactionally checks and locks the live user, enabled verified account and matching auth-v2 session for every service operation. If logout, logout-all, disablement or role change commits first, the operation fails; if consent locks first, it may complete before that change commits. JWT/DB expiry are rechecked after blocking and before commit; expiry can still occur after that last authorization check. Direct service calls cannot use a revoked session. The disclosure route relies on middleware alone, and invitation-recipient policy remains a separate, non-atomic check. Data reads have PostgreSQL statement snapshots: a grant/profile change can commit while an in-flight read returns its earlier snapshot. This switch must never become a production flag; owner/file authorization still has separate middleware-to-operation and streaming race concerns.
- Invitation authorization defaults to **deny all** unless a synthetic per-recipient test policy is supplied. An allow-all or UUID-existence-only policy is not a valid real policy. File routes remain disabled unless a synthetic in-memory S3 transport is explicitly supplied. GC file GET/PUT always return unavailable, even with an active metadata grant; metadata consent is not file consent. Private sub access is test-only and remains blocked from release (including scanning/quarantine and streaming races).

## Reproduce

Install existing project dependencies with Node 22+, then run from the worktree root:

```sh
bash scripts/test-secure-v2-synthetic.sh
node --experimental-strip-types --test server/test/secure-v2-app.test.ts server/test/auth-v2-unit.test.ts server/test/private-certificates-route.test.ts server/test/private-certificate-storage.test.ts
```

The first command creates a new private data directory **inside `.work`**, initializes and starts local PostgreSQL 16 listening on loopback, creates a synthetic test database, clears inherited PostgreSQL/environment configuration, runs the test, stops PostgreSQL, and removes the directory. If PostgreSQL cannot be stopped, it preserves the directory and reports its path for manual cleanup. It explicitly runs the four staged migrations on an exclusively checked-out connection in a random schema against only the throwaway database. No migrations run at app startup. The loopback database uses trust authentication and is not suitable for a shared/untrusted machine; run on an isolated host. It requires PostgreSQL 16 binaries (`PG16_BIN` can point to their directory). The port reservation has a small race; a startup failure must not be retried against any pre-existing cluster. The test checks the server major version.

The end-to-end HTTP test verifies synthetic login and wrong credentials; real JWT/session/role validation; duplicate headers, spoofed IDs and role claims; own and cross-GC access; explicit profile and COI mappings; QR disclosure, issuance, redemption, replay and revocation; default invitation denial and a narrowly scoped synthetic policy; default-off paths; real PostgreSQL metadata with mock-S3 raw PDF upload/download; no GC file access even with consent; bad, expired and logged-out credentials; no legacy paths; configured parser limits; rate-limit denial/errors; a second identity verification after a session is revoked; logout/disable between middleware and the consent transaction with no capability created; and an actual HTTP logout waiting for an in-flight consent write to finish. Separate PostgreSQL race tests force both orderings of logout, logout-all, disable and role change for every consent operation, exercise expiry after blocking, and demonstrate statement-snapshot limits. Synthetic tests do not validate actual AWS, production schemas or all possible interleavings.

## Remaining release blockers

1. Independently review the staged consent transaction/session fix, lock ordering, privileges, trigger interactions, expiry boundary, recipient-policy gap and snapshot semantics. Design and validate appropriate session/revocation semantics separately for owner and file paths; middleware checks alone do not make those operations atomic. Streaming cannot retract bytes already delivered.
2. Real secure account provisioning, verified business/profile/COI ownership, recovery/MFA, key rotation, consent presentation/evidence, recipient authorization, invitation delivery and a narrowly scoped GC file-consent model are not implemented. Metadata grants are not file grants.
3. Implement distributed atomic fail-closed IP/account/subject limits, controlled trusted-proxy handling, request/body/time/concurrency controls and safe monitoring/audit without logging credentials, capabilities, bodies or object keys. Do not use synthetic callback policies or mock transports in production. Establish S3 private-bucket IAM/encryption/block-public-access, malware scanning/quarantine, lifecycle, orphan reconciliation and revocation behavior before any file feature.
4. Independently review every legacy and indirect route, public/static upload, client sharing and frontend integration; rehearse migration, permissions, backup/restore and rollback against a sanitized clone. Verify real schema, privileges and trigger interactions. Finish ingress/TLS/CORS/CSRF, privacy/security review, load and race testing, and an authorized release plan before changing maintenance. This harness is not a security audit or a deployment recommendation.
