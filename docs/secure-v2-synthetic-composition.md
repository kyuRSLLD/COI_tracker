# Secure V2 synthetic composition — test only, disconnected

`server/src/secure-v2-synthetic.ts` composes the actual V2 auth and registration, GC owner, consent/connections, self-reported metadata, private certificate, and opt-in self-reported private-file routers into the standalone `createSecureV2App`. It is **not a production entry point**; it is not imported from the live app or startup, does not listen, run migrations, seed data, load production configuration, or create real S3 or SES clients. Nothing here changes maintenance or legacy routes. Never deploy or mount this harness.

The factory requires `NODE_ENV=test`, a `pg.Pool` whose explicit URL is `127.0.0.1:port/secure_v2_test_*` without URL options, and server-owned synthetic RSA config. Those checks are guardrails only: neither a name nor an environment variable proves disposability. Trusted test callbacks/transports are executable code; the factory cannot prove that a supplied callback is safe or that a supplied transport is genuinely a mock. Use **only** the supplied disposable-cluster runner on a trusted isolated computer, with synthetic data, keys, policies and in-memory object storage. Do not connect this to real/shared databases, real identities, real S3, or a public listener.

## Identity, route and body boundaries

- Public auth is `/api/v2/auth`; owner routes are `/api/v2/gc`; connections are `/api/v2/connections`; files are `/api/v2/certificates`; metadata is `/api/v2/self-reported-coi-metadata`; separately consented self-reported files are `/api/v2/self-reported-private-files`. The outer factory denies legacy/static paths, ambiguous paths and duplicate/malformed Authorization headers, returns generic errors, and sets no-store/security headers.
- Only the exact POST paths `/api/v2/auth/register/request` and `/api/v2/auth/register/confirm` reach the registration router, before the unchanged auth router and its disabled `/register` placeholder. Registration has its own 8 KiB parser. The outer auth pre-limit still applies; registration additionally requires both an explicitly supplied `testRegistrationRateLimit` callback and `unsafeTestOnlyMockSes` SDK transport. Missing dependencies, registration limiter denial/error/timeout, and delivery errors return generic 503; outer pre-limit denials return generic 429 and missing/error/timeout return 503. The registration limiter receives a peer address and a hash of email or token; never log these. It is only a test callback, not abuse protection. Deadlines do not cancel callbacks.
- With a supplied transport only, the real SES adapter constructs a text-only code message with tracking disabled, using fixed synthetic sender/region settings and no SDK client or network. It does not return a code in the HTTP response or generate a verification URL. The callback can still perform arbitrary unsafe work: this seam is trustworthy only when the caller supplies an in-memory mock. Those fixed settings are test data, not deployment guidance. Registration/login verifies email-code access, not phone control, business identity, consent or ownership. A generic 200 confirmation does not prove an account was created.
- The outer protected gate calls the actual `requireAuth`, which verifies the RS256 credential and checks the session/account/current role in PostgreSQL. It rejects any pre-existing `req.securePrincipal` and deliberately does **not** create one. The owner, connections and certificate routers call the adapter, which runs `requireAuth` again, reads only the freshly established `res.locals.authV2`, freezes a copy, and defines a non-writable/non-configurable request principal. A private WeakMap permits repeated adapter calls only after another successful verification and only when subject, role and credential are unchanged; foreign properties are rejected. The metadata router separately reruns the real `requireAuth`, uses its verified response-local principal, and its service independently checks the credential and session. Neither client JSON, query parameters, spoofed identity headers, nor JWT role claims establish identity.
- This ordering matters: the certificate router deletes a prior `securePrincipal` before its own verifier. Pinning at the outer gate would make that deletion throw. The outer gate supplies no such property; the certificate router clears any prior configurable value and the adapter verifies and pins a new value. The outer gate rejects any pre-existing property outright, including non-configurable properties. Do not rearrange, mount behind an identity-pinning middleware, or reuse the adapter with an unreviewed verifier. `res.locals.authV2` is cleared and rebuilt by every real `requireAuth` call.
- The factory's default remains a 64 KiB JSON parser. This concrete composition sets `routersOwnBodyParsing`, so actual router limits work: auth 8 KiB, owner 64 KiB, connections and metadata 4 KiB. The certificate router receives the unconsumed raw request; it validates MIME, length, encoding, and a 10 MiB actual byte limit. JSON/multipart are not valid file uploads. Parser/status conventions vary by router but bodies remain generic. The real proxy must independently enforce body, decompression, header, timeout and concurrency limits.
- An explicitly supplied test rate callback is invoked before auth routes and, on protected routes, before the outer verifier and again with the verified subject. The consent and metadata routers also invoke their own preauth/principal phases. Missing limiter fails closed with 503; non-true is 429; errors/timeouts are 503. The callback receives a TCP peer address, not a trusted proxy-derived client address, and no request body or credential. It is **not** a real distributed limiter or a complete login account-abuse control. Double charging the protected and router scopes is intentional in this harness; real policy budgets need a separately reviewed design. Callback timeouts do not cancel underlying work.
- Consent routes are **disabled by default**, enabled only by the unsafe synthetic-only option. The consent service now independently verifies strict JWTs and transactionally checks and locks the live user, enabled verified account and matching auth-v2 session for every service operation. If logout, logout-all, disablement or role change commits first, the operation fails; if consent locks first, it may complete before that change commits. JWT/DB expiry are rechecked after blocking and before commit; expiry can still occur after that last authorization check. Direct service calls cannot use a revoked session. The disclosure route relies on middleware alone, and invitation-recipient policy remains a separate, non-atomic check. Data reads have PostgreSQL statement snapshots: a grant/profile change can commit while an in-flight read returns its earlier snapshot. This switch must never become a production flag; owner/file authorization still has separate middleware-to-operation and streaming race concerns.
- Metadata is separately **disabled by default**; only `unsafeTestOnlyEnableMetadata: true` injects it in this test harness. It requires distinct affirmative consent for each record and connected GC; profile QR consent alone shares no metadata. No metadata grant provides client access or a document. A distinct, opt-in synthetic self-reported-file router requires an individual file grant for each GC; it never turns metadata consent into file consent.
- Invitation authorization defaults to **deny all** unless a synthetic per-recipient test policy is supplied. An allow-all or UUID-existence-only policy is not a valid real policy. The legacy-shaped `/certificates` mock remains disabled unless a synthetic in-memory S3 transport is explicitly supplied; its GC GET/PUT remain unavailable even with profile consent. The separate self-reported private-files surface instead requires its own explicit synthetic inspector and storage opt-in and an individual file grant. Both are test-only and blocked from release (including scanning/quarantine and revocation concerns).

## Reproduce

Install existing project dependencies with Node 22+, then run from the worktree root:

```sh
bash scripts/test-fresh-sub-registration.sh
node --experimental-strip-types --test server/test/secure-v2-app.test.ts server/test/auth-v2-unit.test.ts server/test/private-certificates-route.test.ts server/test/private-certificate-storage.test.ts server/test/ses-registration-delivery.test.ts
```

The first command creates a private directory inside `.work`, initializes a local PostgreSQL 16 cluster on loopback with synthetic databases, clears inherited database/environment configuration, runs tests serially, stops PostgreSQL and removes the directory. If stopping fails, it preserves the directory for manual cleanup. The combined HTTP test's random schema explicitly runs owner, consent, auth, private certificate metadata, registration, fresh-evidence, self-reported metadata 006, anonymous reports 006, and self-reported private files 007 migrations in that order on an exclusively checked-out connection. Each 006/007 feature has its own version-1 ledger. The self-reported file router is mounted only with an explicit unsafe test-only mock inspector/storage opt-in and remains disabled by default. The synthetic users/contact/phone fixture does not establish compatibility with a real database. Nothing migrates at app startup. Trust authentication is unsuitable for a shared/untrusted machine; use an isolated host. PostgreSQL 16 is required (`PG16_BIN` can override the binary path). Port reservation has a small race; never retry a startup failure against an existing cluster.

The combined test checks the 006 migrations use distinct ledgers and locks, including checksummed reruns, cross-ledger tampering isolation and non-blocking lock independence; 007 uses the metadata lock key and checks its pinned DDL checksum. The anonymous report router remains disconnected; the self-reported file router uses only injected synthetic mocks. The HTTP test covers GC/sub signup and login, names and normalized phone, mock SES command and tracking configuration, generic responses, failures and timeouts, synthetic fresh provenance and registration-to-profile-only sharing and revocation; JWT/session/role checks, spoofed identities, own/cross-GC boundaries, synthetic profile and COI mappings; registration followed by profile-only QR, separate per-record consent, allowed GC, denied other GC and simulated client/admin, revocation and no file access, QR redemption/replay, default-deny invitation policy, mock-S3 access, parser and rate limits, and real session/logout races. Separate race tests exercise both orderings and snapshot limits. Tests do not validate real AWS, production schemas, deployed frontend or all interleavings. See `SELF_REPORTED_PRIVATE_FILES.md` for the optional synthetic real-parser file-service test and its limits.

## Remaining release blockers

1. Independently review the staged consent transaction/session fix, lock ordering, privileges, trigger interactions, expiry boundary, recipient-policy gap and snapshot semantics. Design and validate appropriate session/revocation semantics separately for owner and file paths; middleware checks alone do not make those operations atomic. Streaming cannot retract bytes already delivered.
2. Production-ready account provisioning, independently verified business/COI ownership, recovery/MFA, key rotation, consent presentation/evidence, recipient authorization, invitation delivery and production GC file access are not implemented. The separate prototype file-consent service is not a production implementation. Profile-only v2 grants are neither COI metadata grants nor file grants.
3. Review and deploy suitable distributed atomic fail-closed IP/account/subject limits (the optional PostgreSQL file limiter is not wired), controlled trusted-proxy handling, request/body/time/concurrency controls and safe monitoring/audit without logging credentials, capabilities, bodies or object keys. Do not use synthetic callback policies or mock transports in production. Establish S3 private-bucket IAM/encryption/block-public-access, malware scanning/quarantine, lifecycle, orphan reconciliation and revocation behavior before any file feature.
4. Independently review every legacy and indirect route, public/static upload, client sharing and frontend integration; rehearse migration, permissions, backup/restore and rollback against a sanitized clone. Verify real schema, privileges and trigger interactions. Finish ingress/TLS/CORS/CSRF, privacy/security review, load and race testing, and an authorized release plan before changing maintenance. This harness is not a security audit or a deployment recommendation.
