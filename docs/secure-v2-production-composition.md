# Secure-v2 production-intended composition (unmounted; not release-ready)

`server/src/secure-v2-production.ts` exports `createSecureV2ProductionApp(deps)`. It composes the real auth-v2/registration, GC owner and GC/sub connection routers with `createSecureV2App`; metadata and self-reported private files are explicit independent opt-ins. This is **not** the synthetic factory, a server startup, an entrypoint or a deployment. Nothing imports it from the existing app or index. It constructs an app but does not listen, connect to services, provision resources, run migrations, or seed. It does not change maintenance. **Full production integration is unavailable and must not be inferred from this factory.** It is not a security audit or authorization to deploy.

## Configuration and dependency contract

Pass a trusted server-owned environment object explicitly; the factory never reads `process.env` itself and never falls back to `DATABASE_URL`, legacy SQLite/files, `JWT_SECRET`, legacy auth, cloud clients or test defaults. All settings below are strings. Runtime injection must be protected from requests and unauthorized configuration changes. Missing or invalid required configuration/dependencies throw a single generic startup error before an app is returned. The error does not include the invalid value or cause. Do not log the supplied env, pool options, credentials, keys, raw errors, request bodies, bearer tokens, identity hashes, codes, object keys, documents, or AWS commands. This module emits no logs; injected components and infrastructure must also avoid sensitive logs. Environment secrets remain in process memory: use short-lived runtime secret injection, restrict process/environment access and crash dumps, do not put secrets in source, command histories, build images, `.env` files, or logs, and rotate/restart through a separately reviewed operational process. PEM keys are in-memory signing material, not automatically rotated or zeroized.

Required environment fields:

| Field | Requirement |
| --- | --- |
| `SECURE_V2_CONFIG_VERSION` | Exactly `1`. |
| `SECURE_V2_DB_HOST`, `SECURE_V2_DB_PORT`, `SECURE_V2_DB_NAME`, `SECURE_V2_DB_USER`, `SECURE_V2_DB_PASSWORD` | Explicit dedicated PostgreSQL target and secret; canonical positive decimal port. Exact match to the injected pool, no connection URL or fallback. Names are conservatively syntax-checked. |
| `SECURE_V2_JWT_PRIVATE_KEY_PEM`, `SECURE_V2_JWT_PUBLIC_KEY_PEM` | Server-owned, matching RSA signing private and public-only verification PEMs, at least 2048 bits; validated by `createV2Auth`. No shared-secret fallback. |
| `SECURE_V2_JWT_ISSUER`, `SECURE_V2_JWT_AUDIENCE` | Nonempty exact strings, no whitespace padding/control characters. The JWT implementation is RS256, 15-minute maximum token lifetime, with DB sessions. |
| `SECURE_V2_SES_REGION`, `SECURE_V2_SES_FROM`, `SECURE_V2_SES_TIMEOUT_MS` | Valid SES region and single sender mailbox and canonical integer timeout (100–15000 ms). Sender verification, region access, quotas and deliverability are not checked by construction. |
| `SECURE_V2_METADATA`, `SECURE_V2_FILES` | Each must be exactly `enabled` or `disabled`. Files require metadata enabled. Disabled private mounts still require authentication and then return 503. |
| `SECURE_V2_FILE_S3_BUCKET`, `SECURE_V2_FILE_S3_EXPECTED_OWNER`, `SECURE_V2_FILE_MAX_BYTES`, `SECURE_V2_FILE_S3_DEADLINE_MS`, `SECURE_V2_FILE_UPLOAD_DEADLINE_MS` | Required only when files are enabled. Bucket and 12-digit owner are checked by `privateFileS3ConfigFromEnv`; max is 1–10485760 bytes, S3 deadline 1–120000 ms and upload deadline 1–60000 ms. Numeric strings must be canonical positive decimals. |
| `SECURE_V2_LOGIN_ACCOUNT_HMAC_KEY` | Optional **only together with** `limiter.allowLoginAccount`; canonical unpadded base64url of exactly 32 randomly generated secret bytes. Both absent preserves existing behavior; a partial or invalid configuration fails startup. |

The injected fresh, unused `pg.Pool` must use explicit host, port, database, user, password matching the secure-v2 settings; `options: '-c search_path=public'`; `ssl: { rejectUnauthorized: true }`, optionally with a nonempty trusted CA PEM string; and bounded positive `max` (1–100), `connectionTimeoutMillis` (1000–60000), `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout` (each 1–120000 ms, lock timeout no longer than statement timeout). URL, custom pool client, custom stream, and pool logger are rejected. No connections are checked at construction. A matching host/name does not prove database isolation, schema compatibility, least privilege, or that this is a new database rather than an old one; those are operator responsibilities. The pool is owned and closed by the future integrating process, not by this factory. Injectors and later mutation are trusted; no in-process API can attest the honesty of a `pg.Pool` or prohibit other modules from using one.

The following server-owned dependencies are mandatory, even if a caller expects little traffic:

- `limiter.allow` for scopes `auth`, `protected`, `connections-router`, `metadata-router`, `files-router`, and phases `preauth`/`principal`; plus `limiter.allowRegistration` for the registration router's action, peer address and hashed email/token. These must implement reviewed shared atomic global/peer/identity/subject budgets across instances, with suitable overload protection. The composition adds a two-second deadline, requires literal `true`, sends 429 for scope denial and 503 for errors/timeouts; the registration router sends 503 on denial/error. Timeouts do not cancel uncooperative callbacks. Generic auth limiting supplies only peer IP before authentication; an optional account-aware login interface is described below. Express trust proxy is not enabled: the peer is the socket address, often the proxy. Secure trusted-client attribution and ingress policy remain future work.
- `ses.send` is an injected SES SDK-compatible transport, passed to the existing delivery adapter; no default client is created. The integrating process must supply a reviewed AWS SESv2 client/transport with authenticated TLS, correct region and approved endpoints, restricted short-lived workload credentials, bounded concurrency, retries and no logging of codes, email addresses or commands. The adapter applies its own timeout and disables tracking. Transport injection cannot establish these properties.
- `authorizeRegistrationEmail({email})` and `authorizeInviteRecipient({gcSubject,profileId})` are separate mandatory server-side policies. They must authorize individual recipients; no default or allow-all policy exists. A policy throw, timeout or result other than literal `true` denies. Registration checks email authorization before SES delivery, but after challenge reservation; a denied delivery remains unarmed and best-effort cleanup occurs. Invite authorization occurs before creating the invitation but is a separate non-atomic decision; the policy must be designed around that gap. Email control does not verify business, phone or insurance ownership. No invitation email delivery is provided.
- Only if files are enabled: a real `files.inspector` and `files.s3` must be explicitly injected. The factory constructs the existing immutable version-bound S3 adapter, not local storage. It never constructs an SDK client or scanner. The scanner must completely inspect the exact bytes and fail closed on failure or timeout. The S3 transport must enforce approved AWS endpoints and no redirects; versioning, bucket privacy, encryption, IAM, write-once protection, lifecycle and no alternate access paths require independent infrastructure verification. The interface cannot detect a dishonest adapter. The existing S3 adapter cannot itself enforce no redirects, an explicit release blocker. A successful scan is not proof of safety. See [SELF_REPORTED_PRIVATE_FILES.md](./SELF_REPORTED_PRIVATE_FILES.md), [PRIVATE_FILE_INSPECTION.md](./PRIVATE_FILE_INSPECTION.md), and [PRIVATE_FILE_S3_ADAPTER.md](./PRIVATE_FILE_S3_ADAPTER.md).

The certificate-shaped `/api/v2/certificates` router is deliberately **not** composed and returns 503 after authentication. The self-reported file router is a separate surface and requires its own individual per-file/GC consent; profile and metadata consent do not grant files. Disabling metadata/files is not equivalent to successful readiness. No static uploads, legacy API, client report/share, or alternative storage route is installed. The outer factory rejects ambiguous paths and non-allowlisted prefixes; it authenticates protected requests before router parsing. Routers retain their individual body limits. The verified-principal adapter is shared with the synthetic harness but the production factory never imports or invokes that harness. Authentication verifies fresh RS256 credentials and session/role state before routing; some services also recheck authorization transactionally. Read/stream and policy race limitations remain in the linked docs.

## Optional login-account throttle

To opt in, inject `limiter.allowLoginAccount({ accountHash }): Promise<boolean>` and the key above. There is **no included distributed limiter or production allow-all default**. The trusted adapter must atomically check and count every attempt, including successes and unknown accounts, against a per-account budget shared across all instances; it must not reset the budget on successful login. It needs bounded storage/expiry, overload and concurrency controls, reliable fail-closed operation, and an independently reviewed policy that balances brute-force protection against attacker-triggered account denial of service. A false result yields generic 429; a throw, timeout after two seconds or non-boolean result yields generic 503. Only literal `true` allows the database lookup and password verification. Timed-out work is not cancelled and may still consume a budget later, but cannot resume the login. The account control is **additional to**, not a substitute for, mandatory shared global/peer preauth controls, ingress request limits and scrypt concurrency protection. The factory cannot attest the adapter's behavior.

The existing auth-wide preauth check runs before the auth router's single strict 8 KiB JSON parse. The login handler then applies its existing email normalization and email/password input validation. Invalid input returns 400 without an account check or login attempt. For valid input it HMAC-SHA256s the normalized email with the secret key and the UTF-8 prefix `secure-v2:login-account:v1` followed by a zero byte. Only the 43-character unpadded base64url digest is sent to the account limiter, not email, password, body, or IP. The same normalized address yields the same key regardless of peer and whether the account exists. The auth lookup uses the same normalized email; no second parsing or independent normalization is introduced. No guarantee is made that timing, rate denials or other channels cannot reveal information about traffic. The digest is a stable sensitive pseudonymous identifier, not anonymous data: restrict access and retention and do not log it. Also redact credentials and email at ingress, request logging, APM, error handling and the adapter.

Use a high-entropy, dedicated server-side key from a secret manager, identical on all instances serving the same accounts; syntax checks cannot verify entropy. Protect it and never reuse it for other purposes. Key mismatch, rotation or loss changes all account buckets and can reset protections. Coordinate rotations, including a separately engineered overlap strategy if continuous enforcement is required; this interface does not provide dual-key rotation. If the optional pair is absent, account-targeted login limiting remains unimplemented and a release blocker. Even when configured, suitability of the injected limiter, operational controls and independent security review remain release gates. Direct use of `createV2Auth` outside this composition needs its own equivalent preauth protections and must not expose or log the key or account digest.

## Health and browser policy

`GET /healthz` (and Express's implicit `HEAD`) returns only `{ "status": "live" }` with no-store/security headers. It is unauthenticated process liveness, not database, schema, SES, scanner, S3, authorization, deployment, maintenance, or readiness status. It makes no dependency calls and may return 200 while all backends are unavailable. Other methods and `/readyz` are 404. Restrict health traffic at ingress and design a separate safe readiness check rather than treating liveness as readiness. Existing legacy `/api/health` is not mounted.

This API is not the UI and returns `Permissions-Policy: camera=(), microphone=(), geolocation=()`. That header on API responses does not enable the camera for a document. If a separately served trusted UI needs QR scanning, review its document/iframe and ingress headers and use a narrow `camera=(self)` policy for that document on a secure origin; do not broadly enable camera, microphone or geolocation, change the API policy, or assume this factory serves the frontend.

## Required before any production integration

Complete independent review and integration/security testing of all services, JWT/session and credential lifecycle, account recovery/MFA, consent and ownership evidence, cross-tenant authorization, recipient policy and races. Build and independently verify the required distributed controls and production account-limiter adapter, scanner isolation and packaging, AWS client transport/endpoint and infrastructure controls, file orphan reconciliation/retention, quotas, safe observability, incident response, revocation behavior, and real dependency health/readiness. Review all auth, data and locking paths including expiry/snapshot windows and ambiguous DB/storage commits. Establish safe exclusive ingress, TLS, proxy canonicalization, request/body/time/concurrency limits and separately reviewed UI/CORS/CSRF policies. Complete compatible schema and migration review, least privilege, backups/restore and rollback rehearsal on isolated data before any separately authorized manual migration. Do not turn off maintenance or route alongside the legacy app; secure-v2 alone cannot block another listener or proxy route. No migrations run here.

## Local verification

With existing dependencies and Node 22+, run from this worktree:

```sh
node --experimental-strip-types --test server/test/secure-v2-login-throttle.test.ts server/test/secure-v2-production.test.ts server/test/secure-v2-app.test.ts server/test/auth-v2-unit.test.ts server/test/ses-registration-delivery.test.ts
./node_modules/.bin/tsc --noEmit --target ES2022 --module NodeNext --moduleResolution NodeNext --strict --esModuleInterop --skipLibCheck --allowImportingTsExtensions server/src/secure-v2-production.ts server/src/verified-v2-principal.ts
```

The tests use ephemeral RSA and HMAC keys, a never-connected mock-backed `pg.Pool`, mock SES, scanner and S3, and loopback HTTP. They check missing and malformed configuration, RSA mismatches, unsafe pool options, opt-ins, scope/policy denials, legacy paths, enabled/disabled surfaces and liveness. Account-throttle tests cover ordering and parse bounds, aliases, keyed normalization, shared mock budgets, failures and late results, and successful login. They cannot establish production infrastructure safety, real PostgreSQL behavior, actual SES/S3/clamd behavior, migrations, atomicity of a real multi-instance limiter, UI, or end-to-end release readiness. No real resources are touched.
