# Consented GC/sub relationships — staged, disconnected

**Not a deployed feature or privacy remediation. Keep maintenance mode ON.** This change adds no routes, UI, startup import, automatically run migration, public endpoint, client share link, email, document signing, upload, deployment, or modification/deletion/copying of underlying subcontractor or COI records. It is PostgreSQL-only. Existing legacy routes remain unsafe. Nothing in this module authorizes them. The independent migration ledger `gc_sub_schema_migrations` has version 1 (the file is named `002` to follow the owner-foundation file); it is not a continuation of `owner_foundation_schema_migrations`. Do not edit an applied migration; implement a separately reviewed forward migration or restore a verified backup instead of destructive down SQL.

## Trust model and scope

* Every service method verifies a strict RS256 auth-v2 JWT (server-configured RSA public key of at least 2048 bits, exact issuer and single audience, `sub`, `jti`, `iat`, expiration and at most 15-minute lifetime). `sub` is the only subject used; body IDs, names, email and token role claims never authenticate. The same PostgreSQL schema must include the auth-v2 migration, enabled verified account, current role and matching unrevoked, unexpired token-hash session. The auth issuer and consent service must use matching server-managed keys, issuer and audience; synchronize application and DB clocks. There is no development secret or stateless fallback. Securely extract the raw access credential and keep the independently verified middleware, rate limits and recipient policy. Full provisioning, key rotation, MFA and identity lifecycle remain unimplemented.
* The profile mapping must be established by an independently audited, trusted human/business verification process. `gc_sub_profiles` binds an immutable UUID to exactly one source sub record and one `users.id`; a verification reference is required, but the database does **not** prove the reference or perform verification. No matching by name, email, preexisting `subcontractors.user_id`, or company is allowed. Profile suspension is irreversible at the service/schema level. Profile reassignment, offboarding, remediation, and reuse need a separately reviewed forward process. Tables and identity trigger must not be writable or disableable by end users or legacy principals.
* `gc_sub_coi_ownership` is an additional, explicitly verified mapping from the profile to a specific COI already belonging to that exact subcontractor. No existing records are mapped or backfilled. An unmapped COI remains hidden even if it has the same sub, name or email. In particular, never treat the old GC owner mapping as proof of sub ownership: other GCs may own private records. The service does not implement profile proof, COI proof, or source record creation. Future sub-owned COIs become visible only when an authorized trusted workflow creates/verifies the source and its explicit mapping atomically, with evidence and conflict checks. A blind or mistaken mapping could leak data. Current/future sharing is thus limited to explicitly verified mapped COI metadata, not all records or documents.
* A GC is considered verified here only because its JWT and auth-v2 account/session are valid and its DB user has the live `gc` role. The service does not independently verify the GC's legal identity, business, or authorization to use that role. Role provisioning must be trustworthy; if business verification is required, implement it before any integration. Preview returns the actual authenticated GC user ID and its current name; name is display-only and is not verification or an authorization match.

## Consent and capabilities

`CONSENT_V1` is an exact affirmative input, **not** a default checkbox or a role claim. The future server-controlled UI must show the corresponding exported consent text and require an affirmative action. QR consent states that whichever authenticated GC scans this one-time QR can access current and future explicitly verified sub-owned COI information until revocation. It is necessarily not targeted to a particular GC; if the product requires approval of an identified GC, use the invitation flow or design a separate named-approval flow. The sub must protect the QR and choose when to display it.

1. The authenticated mapped sub calls `issueSubQr` after seeing `QR_CONSENT_V1_TEXT`; the one-time random code is returned once for local QR encoding. A credentialed, live-role GC calls `redeemSubQr`. Redemption atomically consumes the hash, creates/renews the grant and records an event. The code is valid for five minutes, determined by PostgreSQL's clock.
2. The authenticated live-role GC calls `createGcInvite` for a known, independently verified profile ID. The raw one-time invitation is restricted to that profile and expires in seven days. A secure authenticated delivery and inbox are **not implemented**. Before accepting, the verified sub must call `previewGcInvite`, see the returned GC identity and `INVITE_CONSENT_V1_TEXT`, and affirm; `acceptGcInvite` verifies the role and exact profile again and atomically consumes the invitation and grants access. GC invitation creation is not consent. A future UI must not expose profile enumeration: UUID secrecy alone is not authorization, and the caller needs an independently authorized way to select recipients, rate limiting and abuse controls.
3. `revoke` is authorized by the exact current sub profile owner. It revokes that GC's grant, invalidates its outstanding invitations and **all** outstanding QR codes for that sub (because QR codes are not GC-bound). Other GCs' active grants are unaffected. New consent after revocation can intentionally create a fresh grant. Revocation never changes source COIs or sub records. Reads return minimal metadata, never document keys/URLs, coverage or notes. There is no document retrieval service here.

Tokens are 32 cryptographically random bytes encoded in base64url; only a SHA-256 digest is stored. Do not put raw tokens in URLs, logs, analytics, referrers, browser history, screenshots retained beyond need, or client share links. Use TLS, protect storage, scan/delivery, request bodies and access logs. The DB clock must be correct. Capability authorization failures are uniform `UnavailableError`; SQL errors should be logged securely and translated to generic responses by any future integration. Raw service calls are not public API contracts.

Every operation locks current user rows in sorted order, then the actor’s auth-v2 account and session; writes then lock the profile and capability/grant rows. The service rechecks JWT and DB expiry after blocking and before commit; the last check is an authorization point, not a guarantee that expiry cannot occur before commit. Logout/disable/role changes that acquire their relevant locks first cause failure; operations holding those locks first can finish before those changes commit. Role changes and profile suspension serialize with write authorization. A migration-installed users-role trigger permanently revokes this feature's grants and invalidates applicable pending capabilities when an existing `gc` or `sub` role changes, including on subsequent restoration; role revocations produce `revoked_role` events. For a GC, all targeted invites are invalidated; generic QRs belong to their subs and remain usable by other eligible GCs. This trigger writes **only new relationship tables**, not source records. Its invoker must have required relationship-table privileges; otherwise the user-role change fails. Role changes and trusted administration must be tested against the deployed DB's privileges, trigger ordering, existing transactions and retry policy; PostgreSQL deadlock/serialization errors must fail closed and can be retried as whole transactions. Direct SQL that disables or bypasses the trigger invalidates the safety argument. Audit events are useful but not tamper-proof: restrict writes and implement append-only external auditing if required.

Reads check both live roles, active profile, exact grant, and exact COI mapping together in a SQL statement. They are statement-snapshot reads: a request already executing when revocation commits may complete based on its earlier snapshot; previously received or downloaded information cannot be clawed back. Future integration must prevent reuse from caches and recheck authorization for every subsequent request, including any separately designed file access. This service never hands out storage keys.

## Explicit migration and release gates

`migrateGcSubConsentV1` is a function only, never called by application startup. It expects a dedicated checked-out `pg.Client`/`PoolClient` on PostgreSQL, no existing transaction, an explicitly selected search path and trusted schema, and no concurrent use of the same session. It creates its own version/checksum ledger and takes a transaction advisory lock; unknown or tampered history fails closed, and DDL plus ledger commit or roll back together. The migration requires the existing `users`, `subcontractors`, and `cois` schema and creates a redundant `(cois.id, subcontractor_id)` unique index independent of the owner foundation. It also adds a role-change trigger on `users`, so examine deployment constraints, lock duration, privileges, existing triggers and code paths. There is no automatic deployment runner. Before any approved run: preserve maintenance, stop writers, backup and rehearse restoration, inspect actual schema/drift and extensions, test on a sanitized clone, do an independent security/privacy review, and verify constraints and record counts afterward. No real database was touched.

Before enabling anything: independently review and validate session/role lifecycle and revocation semantics, create the real identity-verification and mapping workflows, transactionally integrate sub-owned COI creation with mapping, secure invite delivery and informed consent UI, limit recipient discovery and abuse, integrate/authorize every route/storage operation, implement CSRF protection as appropriate, and test tenant/IDOR, concurrent revocation and all indirect paths. Legacy `requireAuth` has a development-secret fallback and trusts claimed roles; it is not suitable for this service. No claim is made that the incomplete application is production-ready.

## Tests

The integration test rejects non-loopback URLs, URL host overrides, and databases not named `gc_sub_test_*`; it creates and drops a random schema, verifies server major version 16, and does not read app environment configuration. Run only against an explicitly disposable local cluster; URL safeguards alone do not make a real/shared database safe. For example, using an already-started disposable PostgreSQL 16 cluster:

```sh
GC_SUB_TEST_PG_URL=postgresql://ubuntu@127.0.0.1:55489/gc_sub_test_disposable \
  node --experimental-strip-types --test server/test/gc-sub-consent.test.ts server/test/gc-sub-auth-races.test.ts
```

It covers failed/duplicate/tampered migrations, coexistence with owner foundation and unrelated tenant isolation, no name/email guessing, consent gating, issuer/audience/signature/expiration, role downgrade/restoration invalidation, QR/invite expiration and replay, hashed storage, current/future explicit COI mappings, private-field omission, invite preview, sub-only revocation and unchanged source rows, injected atomic rollback, simultaneous single-use redemption, both lock orderings of revoke vs redemption, role changes blocked mid-request, and irreversible profile suspension. The separate auth-race suite covers invalid sessions and account status for every method, both orderings of logout/logout-all/disable/role changes, expiry while blocked, and snapshot boundaries. The tests use representative minimal schemas, not a production-schema rehearsal.
