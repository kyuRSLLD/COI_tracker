# Owner foundation v1 — staged, not enabled

Base: `c06326a8d7b28df39c334f12582911cf543c69c1`. **This is not a privacy remediation by itself. Keep maintenance mode ON.** No existing route, startup, deployment, data, or automatic initialization is changed. The module is not a CLI and cannot run without an explicit caller and connection.

## Model and guarantees

* `owner_subcontractor_connections` explicitly binds one source subcontractor record to exactly one GC user ID, with a primary key on the sub ID and a unique `(owner_user_id, subcontractor_id)` pair. Different GCs cannot own the same physical source record. This is intentionally conservative: future consented multi-GC sharing must use a separate reviewed permission model, not a second owner mapping or a copy of someone else's private data.
* `owner_coi_records` separately binds each source COI to exactly one GC and the same owned subcontractor. Composite foreign keys require both the actual COI-to-sub relationship and the existing GC-to-sub mapping to match. No cascade is specified. Deleting a mapping is **not** a deletion of the source record, and mapped source records cannot be deleted while referenced. This foundation has no deletion or mapping-management API.
* All preexisting and newly inserted unmapped records are quarantined from **these** reads; assigning a sub never implicitly assigns its old COIs. Names, emails, `companies.owner_user_id`, and `subcontractors.user_id` do not establish ownership. There is no fallback. Fresh records need an explicit owner mapping in the same transaction as creation in any future write implementation.
* These queries require a trusted, credential-verified subject ID and join the current `users.role = 'gc'` **in every SQL statement**. They never trust a role in a JWT. Unknown IDs, revoked/downgraded roles, admin/sub accounts, unowned records, and other GCs see no rows. Missing and unauthorized single records both return `undefined`. Authentication and credential verification are the caller's responsibility; this module by itself cannot verify a JWT or prevent an untrusted caller from spoofing a subject.
* Responses are deliberately minimal; COI certificate URLs/keys, coverage, notes and upload tokens are excluded. Sub contact information is still private: the projections are for the exact GC owner, **not for client-share links**. There is no client access or document access feature here.

## Transaction and migration contract

`migrateOwnerFoundationV1` accepts an exclusively held session, not a pool. PostgreSQL: use a checked-out `pg.PoolClient` or connected `pg.Client`; migration uses one transaction and a transaction-scoped advisory lock. SQLite: open a dedicated database connection, enable and verify `PRAGMA foreign_keys = ON` on that connection before invoking, and do not share it; migration uses `BEGIN IMMEDIATE`. The adapters are in `server/src/db/ownerConnection.ts`. Every SQLite connection used for **writes**, not just migration, must enable and verify foreign keys. No nested transaction or simultaneous queries on that connection. All statements and the version/checksum record commit together; failure rolls them back. A matching v1 is a no-op; changed/unknown history fails closed. Never edit an applied migration; create a new forward-only version. The v1 runner intentionally refuses future unknown versions.

Run only as an explicitly approved offline operation after backup, restore rehearsal, production-schema compatibility checks, and a reviewed migration runner is built. Stop all writers, preserve maintenance mode, acquire deployment-level exclusivity, inspect DB permissions and migration history, and verify tables, indexes, constraints and row counts afterward. Index creation can lock or take substantial time. Transactional DDL is supported by the intended PostgreSQL and SQLite engines, not arbitrary database drivers. The ledger checksum identifies the migration text, not out-of-band schema changes; inspect actual constraints if drift is possible. Never retry against a different database after ambiguity without investigation. Roll back a failed transaction; no destructive down migration is provided. Reverting an already committed schema requires a separately reviewed forward repair or verified restore, not deleting tables/data.

## Required integration before any access is enabled

1. Verify the signed credential, issuer/audience/expiry and subject at the server boundary with production-grade secrets; use only its verified subject ID. Never accept `owner_user_id` from a body/query/path. Current `requireAuth` trusts JWT role and has an insecure development-secret fallback; it is not sufficient for production as-is. Call a service that checks the live DB role in each operation, including on writes; do not rely solely on login-time claims. Decide what disabled/deleted users mean; the current schema has no active-user flag.
2. Build reviewed, authenticated create/update/delete operations. Every operation must authorize the exact subject and exact mapping **in the same SQL statement/transaction**, not check then perform an unrestricted write. Prevent COI reparenting and cross-GC references. Insert a source row and its explicit mapping atomically. Do not delete source COIs/subs or dependent data as part of ownership changes; design revocation/retention separately. Do not add admin/global fallback. Unrelated and unowned IDs should be indistinguishable to callers. Re-check access immediately before any storage access.
3. Design a separate, auditable, human-verified reconciliation workflow for historical assignments, with provenance, authorization, consent where needed, conflict handling and reversible mapping changes; don't guess by name/email or silently claim records. The database permits direct trusted SQL mapping writes and does not enforce that `owner_user_id` currently has role `gc`; the service fails closed on non-GC roles. Restrict mapping-table writes to trusted server/operations principals and enforce current GC role and authorization inside any future write transaction. If roles can change concurrently, lock the role row or use an isolation policy that gives the intended revocation guarantee.
4. Replace and test **all** legacy unscoped routes and indirect paths: project links, statistics, uploads, subcontractor portals, admin functions, exports, email, certificate links, object storage and `/uploads`. Audit inherited URLs, caches, logs, token entropy/expiry/revocation and static files. Existing legacy endpoints remain unsafe if maintenance is disabled. Client share/upload tokens are separate capabilities requiring explicit permission and safe redaction; never reuse owner-facing queries/projections as a client bypass. No signed URL or object key should be exposed without authorization on every issuance and an appropriately short expiry.
5. Before release, review legal/privacy policy, production DDL/data drift, authorization and concurrency, independent security review, migration rehearsal on a sanitized copy, backup/restore, deny-by-default integration tests for every route including IDOR and file retrieval, and a deployment/rollback plan. The maintenance switch must remain on until all are approved. This module doesn't introduce row-level security, and legacy DB connections can bypass it.

## Local tests

From `server/`: `node --experimental-strip-types --test test/owner-foundation.test.ts`. SQLite uses `:memory:` exclusively. Optional PostgreSQL: set `OWNER_FOUNDATION_TEST_PG_URL` to an explicitly disposable loopback database named `owner_foundation_test_*`; each run creates and drops a randomly named schema. Never point tests at production or shared data. Tests intentionally seed minimal representative legacy tables and never load application environment configuration. Optional tests are not a substitute for testing on a sanitized clone of the actual deployed schema.
