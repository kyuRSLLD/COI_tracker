# Private certificate API — disconnected, default off

**Not deployed, not a complete security fix, not a reason to disable maintenance.** `privateCertificatesRouter()` is not mounted or imported from startup. With no explicit `enabled: true`, all requests to a mounted router get 503. No production database or AWS resource was contacted, and no production migrations were run. Legacy routes, legacy certificate URL/key columns, local `/uploads`, old links, client views and public assets are unchanged and may still expose data. Review `OWNER_FOUNDATION.md`, `GC_SUB_CONSENT.md`, `PRIVATE-CERTIFICATE-STORAGE.md` and maintenance guidance together; all broader release gates still apply.

## Supported subset and schema coordination

The current `gc_sub_grants` consent text and projections concern explicitly verified COI **information/metadata**, not file access. It is **not file consent**. Both GET and PUT for a verified GC principal intentionally return 503 whether or not that grant exists. No document-grant schema, consent-collection flow, or GC file access is claimed here. Client, public, admin, and other roles cannot upload or download. Supporting a GC later requires a separately reviewed, specific affirmative file-consent grant with identified GC, scope/version, expiry/revocation, appropriate audit, current-role checks, creation/revocation workflow and concurrency policy. Do not reuse the existing metadata grant as file consent.

Only a current `users.role = 'sub'` whose immutable authenticated subject exactly matches `gc_sub_profiles.sub_user_id` can access a COI explicitly present in `gc_sub_coi_ownership`, with matching active profile, subcontractor and actual `cois` parent. No ownership is inferred from a GC owner mapping, `subcontractors.user_id`, name, email, a profile alone, COI's sub alone, or legacy key/URL. The authorization query runs before each operation, the storage callback checks it again, and the actor-bound repository repeats it in the SQL statement that reads or inserts metadata. A missing/foreign/unmapped item yields the same 404. The role in the verified principal cannot override the live DB role. ID format is limited to 1–128 ASCII letters/digits/underscore/hyphen; incompatible existing IDs are inaccessible, not converted. Users have no independent active/disabled flag in the staged schema; account/session lifecycle must be added before use.

`003_private_certificate_metadata.ts` is a manually callable, independent, PostgreSQL-only, transactional migration with checksum ledger and advisory lock. It presupposes the exact staged `002_gc_sub_consent.ts` migration and existing source tables. It creates an immutable one-to-one COI-to-private-object mapping, unique key, allowed MIME and byte-size constraints, and a foreign key to the independently verified COI mapping. No records are backfilled and no existing source columns are altered. Only the service supplies the key; never grant untrusted users write access to these tables. An INSERT cannot replace a record, and a trigger rejects UPDATE/DELETE. Replacement requires a separately reviewed versioning, retention and deletion design; privileged SQL or disabled triggers can bypass protection. The application DB identity should have only the minimum privileges, and other legacy DB writers must not be able to bypass these checks. No RLS is provided.

Coordinate migration review with the current schema inspection: this code assumes `users(id, role)`, `cois(id, subcontractor_id)`, `gc_sub_profiles(id, subcontractor_id, sub_user_id, revoked_at)` and `gc_sub_coi_ownership(coi_id, profile_id, subcontractor_id)` exactly as in the staged migration. The code was inspected against the repository schema, **not the actual deployed DB**. A migration ledger is not a drift detector. Before any independently authorized offline operation: inspect live schema/constraints, triggers and privileges; backup and rehearse restore and migration on a sanitized clone; stop writers; preserve maintenance; select a trusted fixed search path; use an exclusive checked-out idle PostgreSQL client and call the migration explicitly. Review index/table locks and verify resulting constraints and counts. Do not edit applied migration text. No startup runner or production migration execution is included.

## Integration contract

The disabled router requires no configuration. Enabling requires a trusted server-supplied `verifiedMiddleware`, a trusted `pg.Pool` with a fixed safe schema/search path, and a `makeStorage` factory. The middleware must authenticate every request, cryptographically verify the credential, issuer, audience, expiry, immutable subject, credential/session revocation and role, and exclusively set `req.securePrincipal = { subject, role, credential }`. The router clears any prior `securePrincipal` before invoking it; never copy one from a body, query, unverified header, unsigned JWT, client share, or legacy middleware. The required nonempty credential is evidence of the integration contract, **not verification by this router**. The externally supplied middleware must not leak errors or respond with sensitive content. The existing legacy auth middleware and its development fallback are not approved. Use HTTPS, secure cookie and CSRF policy or bearer-token controls as appropriate. No principal/credential or object key should be logged. Middleware/parser order is critical: mount this raw-byte router before body parsers or any middleware that buffers or consumes request bodies, and after required secure network controls. Do not mount behind public/client-share bypasses.

For future reviewed production wiring, a factory may use `createPrivateCertificateStorage({ enabled: true, bucket: trustedConfig.bucket, region: trustedConfig.region, ...dependencies })`, where `dependencies` is the factory's `{ authorize, records }` argument. The injectable `PrivateCertificateStorage` transport is for isolated mocks only; do not use an attacker-controlled, local, fallback or custom S3 transport in production. Configure short-lived server credentials, dedicated private bucket, block-public-access, TLS-only, encryption and least privilege as detailed in `PRIVATE-CERTIFICATE-STORAGE.md`. There is no external S3 test here. The router itself does not create a pool, configure a bucket, read environment flags, start a server, or mount itself.

`PUT /:certificateId` accepts only a raw binary body (not multipart/JSON), exactly one of `application/pdf`, `image/jpeg`, `image/png`, `image/webp` as Content-Type, and no query parameters or content encoding other than identity. The service verifies signature against MIME and limits both declared and actual size to 10 MiB. No client-supplied key, path, filename, URL or metadata record is accepted. Success is 201 with `{ mime, size }`; immutable duplicates may leave an orphan and return 503, never replace metadata. `GET /:certificateId` returns only an attachment stream with a fixed filename, `nosniff` and `Cache-Control: private, no-store`; no redirect, signed URL, object key or metadata JSON. Early errors use generic 400/401/404/503 and no-store; an error after streaming begins terminates the response rather than emitting internals. Rejected uploads close the connection. Actual byte counts and type are checked against trusted metadata on download. Cancellation tears down the input/output stream and forwards an abort signal to S3 requests; cancellation is best effort and cannot undo committed writes or bytes already sent. Proxy buffering, access logs, middleware and caches can negate these properties; configure and test them explicitly.

Authorization uses PostgreSQL statement snapshots, not a transaction spanning streaming. A revoke/role change committed before a fresh query is observed, but already authorized in-flight S3 work can race revocation, and delivered bytes cannot be recalled. A metadata insert rechecks current ownership in the insert statement but a concurrent commit can still be ordered after its snapshot. If stronger semantics are required, design coordinated locks, grant/versioning and cancellation across all writers. Similarly, cancellation during a database operation or after S3 receives bytes does not guarantee rollback. S3 write followed by an uncertain/failed DB insert can leave an orphan; do not blindly delete after error. A reviewed, delayed, race-safe reconciliation process, idempotency, retention, monitoring and safe audit are still needed.

## Release blockers and resource safety

MIME signatures are not full parsing, malware detection, sanitization, content disarm or bomb protection. **Malware scanning and quarantine are not implemented**; clean-state verification, full format validation, safe sandboxing and appropriate threat handling are mandatory before enabling real uploads or downloads. Uploads buffer the entire body (up to 10 MiB plus copies). Add upstream body/time limits, per-user rate, bandwidth and concurrency limits, connection/statement/lock timeouts, abuse monitoring and a bounded process memory budget. Validate failure behavior at proxies and SDK. The current tests are synthetic and do not establish security of the rest of the app, identity provider, production schema, network, real S3 policies, CDN, historical data or consent UX. Complete independent security/privacy review, legacy-path remediation, historical object inventory/migration and controlled rollout/rollback before any availability.
