# Private self-reported file S3 adapter — isolated prototype

`server/src/services/privateFileS3Storage.ts` implements `ImmutablePrivateStorage` without constructing an SDK client or wiring an app, route, scanner, migration, credentials, bucket, or deployment. An opt-in in the separate [unmounted production-intended composition](./secure-v2-production-composition.md) now constructs the adapter with an injected client; this does not wire startup or establish production readiness. Tests inject a synthetic SDK client. There are no public or presigned URLs, listing/deleting APIs, raw SDK errors, or data logs. The adapter only accepts the service's generated keys `private-coi/<64 lowercase hex>`, the four service MIME types, and objects from 1 byte to 10 MiB (or a lower configured maximum). The client, configuration, S3 endpoint and AWS credentials are trusted server-side dependencies, not request parameters. A dishonest injected client or S3-compatible endpoint can fabricate evidence; this design assumes genuine AWS S3 over authenticated TLS and trusted SDK behavior.

## Integrity and exact versions

The adapter snapshots the input, computes SHA-256 locally, and performs one `PutObject` with `IfNoneMatch: *`, the exact content length, and the SHA-256 checksum algorithm and value. It does not use multipart upload. AWS documents that S3 validates a provided single-part checksum against the received object and rejects a mismatch, and that PutObject checksums cover the full object. The adapter then requires a nonempty, non-`null` version from the PUT and separately requests `HeadObject` on that exact version with checksum mode enabled. It compares S3's checksum, length and Content-Type to its own snapshot, and checks the returned version. Only then does it return a receipt derived from the HeadObject evidence. An echoed PUT checksum, ETag, user metadata, a missing checksum, a composite checksum, or length alone is never proof. AWS may omit the checksum-type header; absence is accepted because this adapter's successful single-part PUT has full-object checksum semantics. A present non-`FULL_OBJECT` type is rejected. The returned checksum must be canonical Base64 SHA-256.

Reads request the exact version with checksum mode, require the matching response version, checksum and content length, and stream into bounded memory. `getVersion(key, version, maxBytes)` requires a positive safe integer and enforces the lower of the caller's bound and configured maximum on headers and chunks before copying them. A transport can still allocate an oversized single chunk before the adapter sees it. The adapter rejects partial/range responses, delete markers, incorrect lengths, excessive data, invalid chunks, stream errors, SHA-256 mismatch and incomplete streams. It returns no bytes until the complete stream is verified. The service also checks the returned version, size and digest against the authenticated database row; neither layer replaces the other. AWS notes the exact-version read requires `s3:GetObjectVersion`. The adapter expects a Node.js SDK `Readable` body; it is not a browser adapter.

Each operation has one deadline covering the SDK requests and stream consumption. It starts after the synchronous upload snapshot and initial hash; event-loop stalls can also delay timer execution. `putNew` also accepts the service's optional abort signal and propagates cancellation to the SDK; a pre-aborted signal prevents a request. The adapter aborts the SDK signal and destroys an active body on timeout. SDK transports must honor abort for prompt resource cleanup; the caller still gets a generic failure even with an uncooperative client. A write may commit before an error, cancellation, timeout, missing version, failed HEAD, or lost response. No automatic reconciliation or deletion is attempted, and no retry is attempted by the adapter. Configure a reviewed SDK client's retry behavior, preferably `maxAttempts: 1`, to avoid hidden retries; even this does not make a timeout definitively unsuccessful.

Sources: [S3 PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [S3 upload integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html), [S3 HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html), [S3 GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html).

## Explicit configuration

Call `privateFileS3ConfigFromEnv` with a server-owned environment object if environment configuration is desired. All four values are required; there are no defaults or fallbacks:

- `PRIVATE_FILE_S3_BUCKET`: general-purpose bucket name, not an ARN, access-point alias, directory bucket, endpoint or URL. Syntax is validated; existence, ownership, bucket type and account-regional namespace provisioning are not verified by parsing.
- `PRIVATE_FILE_S3_EXPECTED_BUCKET_OWNER`: exact 12-digit account ID, sent in every request so S3 rejects an owner mismatch.
- `PRIVATE_FILE_S3_MAX_BYTES`: canonical positive decimal integer at most `10485760`; align it with the service's maximum and upstream request limits.
- `PRIVATE_FILE_S3_DEADLINE_MS`: canonical positive decimal integer from 1 to `120000`, covering the whole adapter operation.

The factory separately validates numeric config and snapshots it. The two numeric limit fields must not contain spaces, signs, decimals, leading zeroes or exponent notation; the account ID is exactly 12 digits and may begin with zero. A trusted composition root must inject a properly configured AWS SDK `S3Client` with the correct region, AWS endpoint, TLS, SigV4, credentials from an approved workload role, bounded connections and retries. No SDK client is created or configured here; this module cannot verify its region, endpoint, credential source, retries, logger, or bucket policy. **Unresolved release blocker:** the adapter cannot observe or reject redirects followed internally by an injected SDK transport, or independently enforce the destination. A future trusted client/transport and network policy must enforce no redirects and approved endpoints, with integration tests, before this meets the service's redirect/SSRF requirement. Do not point it at an untrusted custom endpoint or configure SDK request/response/body logging. Restrict telemetry to approved aggregate status and timing, without filenames, keys, versions, hashes, document content, or raw SDK errors. Runtime config validation is not proof of AWS configuration.

## Mandatory infrastructure and privilege controls

Before any deployment, create and independently verify a dedicated general-purpose bucket with **versioning Enabled**, not suspended, and ensure that configuration cannot be changed by the application. This adapter rejects missing and literal `null` version IDs but does not itself call `GetBucketVersioning` or monitor configuration drift. Directory buckets do not meet this design's versioning requirement. Set S3 Block Public Access at account and bucket levels, bucket-owner-enforced object ownership with ACLs disabled, private-only bucket/access-point policies and TLS-only transport. Do not grant public or browser direct access. Review all identity, resource, cross-account, access-point, organization and VPC endpoint policies together; no presigning or alternate legacy download path may expose the prefix. No ACL is sent by this adapter.

Give the application workload role only `s3:PutObject` and `s3:GetObjectVersion` on the exact bucket and `private-coi/*` object resources (plus required KMS permissions when using SSE-KMS). The versioned HEAD uses the relevant version-read permission. Do not grant this runtime role list, delete, delete-version, bucket configuration, public access, ACL, or unversioned reads. Bucket policies should require `If-None-Match: *` on all relevant writes and prevent other principals from bypassing this condition or writing to the prefix; validate policy conditions and any service integrations in a dedicated nonproduction account before adoption. AWS's condition applies only to the **current** version: if a delete marker is current, a new conditional write can succeed even when prior versions exist. Deny ordinary delete and delete-version to all relevant principals, prevent lifecycle rules from introducing delete markers or deleting protected versions, and govern privileged break-glass/reconciliation separately. If strict permanent key non-reuse is required even after any privileged deletion, maintain an independent durable non-reuse registry and controls; this adapter alone cannot establish it. Versioning and an `If-None-Match` request alone do not enforce permanent write-once behavior. Object Lock may protect retained versions but does not itself prevent new versions or delete markers; assess retention, costs and legal obligations independently. See [conditional write behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) and [enforcing conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).

Require reviewed bucket default server-side encryption and enforce it with bucket policy. SSE-S3 avoids application-managed keys; if using SSE-KMS, pin the intended KMS key via policy, scope KMS key and IAM grants to this workload and bucket, and verify `kms:GenerateDataKey` and `kms:Decrypt` where AWS requires them for PUT and checksum-enabled HEAD/GET. Do not grant key administration to the application. This adapter sends no explicit SSE headers and does not verify the returned encryption details; encryption controls and monitoring are external production prerequisites. AWS's HeadObject guidance discusses KMS permission requirements at both the general operation level and checksum-mode section; validate the effective minimum in the actual environment rather than assuming checksum access. See [S3 SSE-KMS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html).

## Orchestration and remaining blockers

The existing file service first creates a durable pending reservation, scans, writes, then promotes to ready only after evidence validation and a fresh authorization transaction. S3 and PostgreSQL are not atomic. On any uncertain write, failed proof, session loss, process death or promotion failure, the object must remain private and the pending/orphan record must never become downloadable automatically. A separately authorized, audited reconciliation process must distinguish live uploads from abandoned reservations, discover exact versions, avoid deleting versions referenced by ready rows, and handle retention and ambiguous outcomes. It is not implemented here. Never retry the same key blindly after ambiguity or assume failure means no object exists.

Production remains blocked on infrastructure and IAM verification, actual isolated scanner deployment, integration security review, workload-role/client construction, endpoint and access-path verification, inbound quotas/deadlines/concurrency, memory and database-lock capacity, authorization and safe HTTP download design, reconciliation/retention, observability privacy, incident response, backups and real environment-specific integration testing. Synthetic tests prove only local control flow and cannot prove S3 behavior, policies or operational immutability. No AWS integration test, cloud connection, resource creation, production wiring, deployment or migration has been performed.

Run locally with existing installed dependencies and Node 22: `npm run test:private-file-s3 --workspace=server`. The tests exclusively use in-memory synthetic SDK responses and no AWS credentials or network.
