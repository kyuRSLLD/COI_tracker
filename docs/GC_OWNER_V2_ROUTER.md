# GC owner API v2 — staged and disconnected

**Not a deployment or privacy remediation. Keep maintenance enabled.** `server/src/routes/gcOwnerV2.ts` exports `createGcOwnerV2Router({ pool, authenticate })`. It is not imported, mounted, or reachable in the legacy app. This work changes no migration, app startup, package, or legacy route. The routes below are paths relative to the *proposed* `/api/v2` mount; do not mount in production until all release gates are met.

## Trusted identity boundary

The mandatory `authenticate` Express middleware must validate the credential and establish **only** `req.securePrincipal = { subject: string, role: 'gc' | 'sub' | 'admin', credential: string }` before calling `next()`. `subject` must be the immutable user ID proven by that credential, not a request body, URL, query, arbitrary header, or a user-provided ID. `role` must be the current trusted role, not just an old claim. The credential must itself be verified, nonempty, and handled confidentially. The middleware must pin the property and freeze the value (for example, `Object.defineProperty(req, 'securePrincipal', { value: Object.freeze(principal), writable: false, configurable: false })`), reject absent/invalid/revoked sessions, and handle asynchronous errors in Express 4. Upstream code must not be able to prepopulate or replace this property. A middleware that merely copies request data into `securePrincipal` defeats the security model. This router cannot verify the supplied middleware; **no production authentication/session implementation is included**. The tests' fixed synthetic tokens are not authentication code for production. The legacy authentication middleware is not approved for this boundary.

The router checks the principal shape, rejects non-GC roles, and snapshots only the subject. It also checks the current database role, and the owner services independently check live `users.role = 'gc'` together with the exact ownership mappings in their queries or write transactions. Admin is not a GC override. The preliminary role/record checks permit an empty collection for an authorized GC while returning 404 for a revoked/unknown principal or an absent/foreign/unmapped target; they do not authorize mutations in place of the service transaction. An in-flight read that completed just before revocation can still be returned; multi-query lists are not an atomic revocation snapshot. Writes lock the current user role and ownership mapping in the service transaction (see `OWNER_WRITES.md`). Existing schema has no disabled-account flag. The router's `credential` is never returned, persisted, or used as the owner ID.

## Routes and data

* `GET /subcontractors`: owner's mapped records; 200 array, including `[]` if none.
* `GET /subcontractors/:id`, `POST /subcontractors`, `PATCH /subcontractors/:id`.
* `GET /subcontractors/:id/cois`, `POST /subcontractors/:id/cois`: the parent comes exclusively from the path; a `subcontractor_id` body field is rejected.
* `GET /cois/:id`, `PATCH /cois/:id`.

Creates return 201 and updates 200 with only `{ "id": "..." }`. Read projections are explicit: subcontractor `id`, `company_name`, `trade`, `contact_person`, `phone`, `email`, `status`; COI `id`, `subcontractor_id`, `carrier`, `effective_date`, `expiration_date`, `status`. This includes private contact data and is **not** a client-safe or public projection. No certificate key, URL, name, token, coverage, policy number, notes, or credential is returned. Responses carry `Cache-Control: no-store`. Unknown methods/paths, including every DELETE, return 404; there is no destructive or global delete. No reparenting, implicit legacy assignment, admin override, or client access is provided. Body allowlists, field constraints and date validation are defined in `OWNER_WRITES.md`. Writes and reads never accept a request owner ID as authority. Service results are projected again at the HTTP boundary.

Missing/invalid principal is 401; non-GC, missing or foreign targets are the same generic 404. Invalid JSON or input is 400; an over-64-KiB router JSON body is 413; storage or unexpected middleware failures are sanitized 503. JSON parsing occurs before target lookup, so malformed/oversized payloads can be rejected before the 404 check. An upstream parser may alter or preempt this behavior: integration must configure and test consistent bounded parsing and sanitized errors. Never reflect/log SQL, raw credentials, request bodies, driver errors, or stack traces; an authenticator that directly sends its own response must also sanitize it. No response should be cached or logged as client-facing data.

## Connection and transaction contract

Supply a trusted, dedicated PostgreSQL `pg.Pool` with correctly configured TLS, least-privilege grants, clean idle sessions, and bounded connection/statement/lock timeouts. Each request checks out one `PoolClient`, creates `postgresOwnerConnection(client)`, performs its services serially on that client, then releases it. It never passes the pool to a transaction and never shares a checked-out client concurrently. Any thrown operation error destroys the client rather than returning a possibly poisoned session to the pool. Write storage failures, especially ambiguous COMMIT/ROLLBACK, may have uncertain outcome: investigate and reconcile; **do not blindly retry**. The service assumes READ COMMITTED, no outer transaction, and compatible, already-reviewed schema and enforced owner constraints. The router does not run or install migrations. Direct privileged SQL or legacy routes can bypass these checks; no RLS is provided.

## Incomplete / release blockers

* Production identity/session authentication, session revocation, active-user semantics, CSRF protection for cookie sessions, CORS/origin policy, credential security, and end-to-end security review are not supplied. The required session middleware will be integrated separately. Do not accept the test middleware.
* Projects and project-subcontractor associations, client sharing, public links, client redaction, upload portals, and all legacy indirect access paths are **not** implemented or secured here. The owner contact projection must never be reused for clients.
* Certificate upload, file retrieval, private object authorization, short-lived download links, scanning, document lifecycle, metadata and coverage are **not** implemented. Neither storage locations nor credentials are exposed by these routes.
* No production migration, data reconciliation, audit trail, quota/rate limit, pagination, idempotency/reconciliation after an ambiguous write, retention/deletion workflow, disabled-user handling, monitoring, or production schema compatibility validation is provided. List results are unbounded; operational controls and pagination are needed before broad production use.
* Reconcile historical records only through a separately authorized, reviewed process; never infer ownership from matching names or email. Replace/test **all** legacy routes, static uploads, sharing, emails, admin, statistics, and indirect data flows. Complete privacy/security review, synthetic and sanitized-clone tests, schema and grants review, migration and restore rehearsal, and a deployment/rollback plan before any maintenance change. See `OWNER_FOUNDATION.md`, `OWNER_WRITES.md`, and `GC_SUB_CONSENT.md`.

## Tests

With Node 22 and existing dependencies installed, create a fresh **local disposable** PostgreSQL database named `owner_foundation_test_*` on a loopback-only disposable cluster, then from repository root run:

```sh
GC_OWNER_V2_TEST_PG_URL=postgresql://USER@127.0.0.1:PORT/owner_foundation_test_v2 \
  node --experimental-strip-types --test server/test/gc-owner-v2.test.ts
```

The test requires that explicit URL, forbids URL options/non-loopback hosts/names outside the disposable pattern, creates and drops a random schema containing synthetic tables and constraints, and never loads application configuration or runs an application migration. It runs real HTTP requests through a synthetic verifying middleware and real pooled PostgreSQL connections. It covers forged/missing/malformed principals, non-GC and stale/revoked/unknown roles, cross-GC and unmapped records, create/get/list/update, invalid/reparenting/certificate fields, safe output, no DELETE, JSON errors/size, concurrent writes, sanitized storage errors, destroyed failing sessions, and rollback. It is not a test of the pending production session middleware, deployment, storage, client sharing, real schema, or all legacy paths. Never target production, a shared database, or a real-data clone. Existing `owner-foundation.test.ts` and `owner-writes.test.ts` provide separate synthetic SQLite/PostgreSQL service and concurrency coverage.
