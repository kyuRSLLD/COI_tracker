# Standalone V2 sign-in and registration UI

This is a **disconnected review artifact**, not a production auth migration or release approval. It does not modify the production entry point, route, existing login, server, provider configuration, or schema. The worktree is based on `b8d3ff6ab780237def08dee55ea1bcda84ac0124`. Existing V2 auth and registration are staged components; their router composition, real delivery, production data and authorization remain separate work. See `docs/AUTH_V2.md`, `docs/REGISTRATION_V2.md`, and the secure app's own release documentation. Keep maintenance and existing release restrictions in place.

## Component and API contract

Import `V2Auth` from `client/src/v2-auth/V2Auth.tsx`. It uses the existing React, lucide and Tailwind theme (including the project's `brand` colors and `shadow-card`). Ensure Tailwind scans the component and load the existing Tailwind stylesheet. No router is required. Pass an optional `onAuthenticated(session)` callback, where `session` is `{ token: string, token_type: 'Bearer', expires_in: number, expiresAt: number }`. The first three fields come from the login response; `expiresAt` is a local millisecond deadline computed from request start, the shorter of the response TTL and 900 seconds, less one second for whole-second JWT timestamps. A response arriving after this deadline is rejected. The callback occurs **only after a valid, still-usable 200 login response**, never after registration. The host may then route and must retain the credential only in memory, send it as a Bearer header to reviewed V2 endpoints over HTTPS, handle its expiry, failures, logout/revocation, and clear it on logout and unmount. The local deadline is not server authorization and timer throttling or clock changes can delay cleanup. No refresh flow is supplied. If no callback is provided, the component displays a signed-in notice and discards the credential; it does not provide a working session or destination.

- Login sends only `{email, password}` to `POST /api/v2/auth/login`. Bad credentials and service unavailability are distinct; response text is not rendered. Email is normalized like the server. Existing users are not required by this UI to meet the *new-registration* password minimum when signing in.
- Registration starts with only `{email}` to `POST /api/v2/auth/register/request`. A 202 means only that, **if eligible**, the user should check email. It does not confirm an account or inbox delivery. A 503 or network error is presented as unavailable or uncertain, not success; a delivery outcome can be ambiguous.
- The next step asks the email recipient for the canonical 43-character base64url code, first and last name, complete US phone without extension, password, and role (`gc` or `sub`). Subcontractors must also enter company name and trade. Confirmation sends exactly `{token, role, password, first_name, last_name, phone}` plus `{company_name, trade}` only for `sub` to `POST /api/v2/auth/register/confirm`. No email or public admin role is sent. Passwords require at least 12 Unicode code points and no more than 256 UTF-8 bytes; names and business fields follow the server's length/control-character limits. The client checks phone syntax; the server remains authoritative and applies libphonenumber's US validity rules. The code is manually entered, not a URL. The challenge has a 10-minute server lifetime.
- A generic confirmation 200 is **not proof** of account creation: it can also mean expired/used code or an existing account. The screen explicitly says this and directs the person to try signing in. It does not call the completion callback. A 400 identifies invalid input only generically; network/503 outcomes remain uncertain and recommend trying login before another registration attempt.

Requests use same-origin relative paths, JSON POST bodies, `credentials: 'omit'`, `cache: 'no-store'`, `redirect: 'error'`, and `referrerPolicy: 'no-referrer'`. The component never persists tokens/passwords in web storage, URLs, query strings, logs, or analytics. Verification code and password live in component state only as needed, are cleared on step change/success, and are not displayed after submission. No raw response error or HTML is inserted into the DOM. No provider settings or credentials are requested from the user. The browser, password manager, network instrumentation, extensions, memory snapshots, and host callback are separate trust boundaries; in-memory storage **does not protect against XSS**. Do not capture screenshots, traces, request bodies or logs containing actual credentials or codes.

## Integration and security constraints

The standalone preview has **no API proxy and no real backend**. Any future host must serve the UI and reviewed V2 API from the same HTTPS origin, correctly compose both auth and registration routers at `/api/v2/auth`, configure trusted server-side email delivery and fail-closed shared rate limits, and review origin/CORS/proxy behavior. Do not pass provider credentials into client code. The staged secure app defaults to unavailable without supplied routers and does not automatically enable registration. Registration requires its reviewed schema and server dependencies. Review the code's exact routing/parser contracts; do not mount an unsafe legacy stack as a shortcut.

A production host needs strong XSS prevention, a restrictive CSP appropriate to its frontend, safe output encoding (never use `dangerouslySetInnerHTML` for untrusted data), dependency/third-party-script review, no token-bearing URLs, no credential logging, secure HTTPS, no-store responses, and appropriate headers; there is no way for this component alone to guarantee XSS safety. `secure-v2-app.ts` sets an API-oriented `default-src 'none'` CSP; a separately reviewed policy is needed if HTML is ever served from that server. Bearer tokens are accessible to scripts executing in the origin. The callback and surrounding host must follow the same handling rules. Explicitly assess browser autofill, extensions, error telemetry, analytics and network capture.

Account recovery, password reset/change, MFA, real delivery and abuse monitoring, and end-to-end operational support are not supplied here. Legacy accounts/password hashes are not migrated, v2 registration does not claim an existing legacy account, and email control is not verified business identity or COI ownership. Registration creates corresponding fresh records in `auth_v2_sub_profiles` and `gc_sub_profiles` with immutable email-control-only provenance. The names of legacy verification columns do not mean business identity or insurance was verified. Only separate profile-only v2 consent is supported; a GC cannot see COIs or documents through it. Existing profiles and COIs are not claimed or linked. Do not infer ownership from email, name, or self-asserted company/trade. Review legacy endpoints/authorization, DB compatibility and migrations, consent identity, session races, independent security/privacy assessment, delivery, rate limits, incident response and rollback before any release. See the linked existing docs for the full gates.

## Preview and tests

With this repository's Node dependencies installed, from `client/`:

```sh
npm exec vite -- --config v2-auth-preview/vite.config.ts --host 127.0.0.1 --port 5178 --strictPort
# Open /v2-auth-preview/index.html. Requests intentionally have no real API backend.
npm exec vite -- --config v2-auth-preview/vite.config.ts build
```

From the worktree root, `npm run build` runs the normal client TypeScript/Vite build and server build. With Python Playwright installed and Chromium available at `/usr/bin/chromium`, run `python3 client/tests/v2-auth/test_auth.py` while the preview is running. It intercepts all test auth calls and uses **synthetic data only**; it tests request shapes, GC/sub differences, generic results, unavailable/network errors, validation, login, callback, storage/URL, basic response injection handling and mobile overflow. Screenshots in `client/tests/v2-auth/screenshots/` contain blank/synthetic data. The checks do not test a real server, provider, production CSP, assistive technologies, or security of a deployed host. `client/tests/v2-auth/callback.*` is a test-only host using a synthetic credential.
