# Auth v2 foundation — staged and disconnected

**Keep maintenance ON. This is not deployed, mounted, a replacement for legacy auth, or a privacy remediation.** It makes no changes to `app.ts`, startup, existing accounts or source data, and runs no migration automatically. Legacy endpoints and legacy `requireAuth` remain unsuitable for release. Do not expose the app until all legacy paths, document access, and authorization have independently been remediated and reviewed.

## Configuration and mounting contract

`createV2Auth(pool, { privateKey, publicKey, issuer, audience })` from `server/src/v2/auth.ts` returns `{ router, requireAuth }`. Pass a server-managed PostgreSQL `pg.Pool` using verified TLS and an explicitly set, trusted schema/search path. The constructor fails if a key is missing, is not RSA, is less than 2048 bits, or the public and private keys do not match; no development key, symmetric alternative, or fallback exists. Configuration must come from server-only secret management (for example `AUTH_V2_PRIVATE_KEY_PEM`, `AUTH_V2_PUBLIC_KEY_PEM`, `AUTH_V2_ISSUER`, and `AUTH_V2_AUDIENCE` injected by the future host); the module does not read environment variables itself. Distribute only the public key to verifiers. Never put the private key or values into browser bundles, source control, logs, or test fixtures. The issuer, audience, and PEM public key must be the same values used when constructing `gcSubConsentService`. Do not share this signing key with other JWT issuers or uses. Synchronize application and PostgreSQL clocks.

For a future dedicated v2 server, mount `router` at `/api/v2/auth` and put `requireAuth` on **every** protected route. On success, the middleware sets `res.locals.authV2` to `{ subject, role, credential }`: subject is the verified JWT `sub` equal to the immutable `users.id`, role is freshly read from the database, and credential is the original verified bearer JWT for a downstream service. Treat the context as server-only; never echo `credential`, use body/path/email as identity, or trust a token role. Supply the credential to the consent service only after this middleware, and do not expose a way to invoke that service that bypasses the middleware. Example for a future server (illustrative only; **not a release approval**):

```ts
const auth = createV2Auth(pool, { privateKey, publicKey, issuer, audience })
app.use('/api/v2/auth', auth.router)
app.get('/api/v2/example', auth.requireAuth, async (_req, res) => {
  const { subject, role, credential } = res.locals.authV2 as V2AuthContext
  // Authorize the actual operation again with live DB checks, and do not return credential.
})
```

The JWT is RS256 with exact single-string issuer and audience, `sub`, `jti`, `iat` and expiration; its lifetime is 15 minutes, with no refresh token. The middleware validates algorithm, signature, issuer, audience, required expiry and lifetime, then requires a matching SHA-256 hash of the *entire* token in an unrevoked, unexpired DB session, an enabled verified v2 account and a current `gc`, `sub`, or `admin` role on every request. JWT role claims are ignored. DB errors fail closed with a generic 503. No role or personal details are embedded by the issuer. `GET /me` returns just subject and current role. `POST /logout` revokes the current session; `POST /logout-all` locks the user and revokes all then-current sessions, serializing against in-flight issuance. A subsequent login with the password legitimately creates a new session. JWTs and any intermediate credential must not be logged or put in URLs, analytics or referrers.

**Revocation boundary:** `requireAuth` alone is a point-in-time read: other owner/file operations may proceed after concurrent logout, disablement or expiry. The staged `gcSubConsentService` now independently verifies the strict JWT and, in every service operation, locks the current user, enabled verified account and matching unrevoked session in a READ COMMITTED transaction, then rechecks JWT and database expiry after blocking and again before commit. A completed logout/disable/role change first causes consent to fail; an operation holding the relevant locks first may finish before the competing change commits. The last expiry check is an authorization point, not a guarantee of validity at commit. Direct consent calls also require a valid session, but this does **not** replace trusted authentication middleware, rate limits, or recipient policy. The `/consent` disclosure route does not call the service and relies on middleware. Concurrent grant revocation or profile changes may still be invisible to an already-started data statement's snapshot; delivered data cannot be retracted. Owner and file routes have not gained these transaction-level session semantics; their writes, reads and streams require separate design and independent review before exposure. Consent session binding does not constitute a release approval.

**Bearer-only transport:** Send `Authorization: Bearer <JWT>` over HTTPS; cookies, query parameters and bodies are never read as auth credentials. Duplicate Authorization headers are rejected. The router sends `Cache-Control: no-store`. Browser clients should hold tokens in memory, avoid persistent storage, use strong XSS controls/CSP, tightly restricted CORS, and never enable a wildcard credentialed cross-origin policy. Avoid ambient cookie auth; if a future design adds cookies, separately design CSRF protections, SameSite, Secure and HttpOnly behavior. TLS must be enforced end-to-end, including any reverse proxy, and Authorization redacted at proxies, APM and application logs. The parent server must ensure parser failures and security headers are also safe for other routers.

## Registration and lifecycle

`POST /register` rejects any role other than `gc` or `sub` (including public admin) with 400 and otherwise returns 503. It creates **no user, account, verified-email claim, or subcontractor/profile mapping**. Email delivery and verification are not implemented; this fails closed rather than pretending verification succeeded. No existing sub record is ever associated by email, name or legacy `subcontractors.user_id`. The separate staged registration router described in [REGISTRATION_V2.md](./REGISTRATION_V2.md) can create a fresh email-control-only application profile from scratch; that does not verify a business, authority or historical ownership. Any historical/business identity mapping requires a separate trusted workflow and independently verified evidence, not just a reference string.

Login only works for an explicitly provisioned `auth_v2_accounts` row, bound to an existing `users.id` by an independently audited identity process, with a verified login address, verification timestamp and nonempty evidence reference, `enabled=true`, and a v2 scrypt hash. The database stores those assertions but cannot prove them. There is no automatic migration of legacy password hashes or implicit claim that legacy email addresses are verified. A trusted offline provisioning workflow can call `hashV2Password` with a securely obtained password and establish the row only after proving email control and the binding to that exact user. The hash uses a random 128-bit salt and scrypt N=32768, r=8, p=1, 256-bit output; passwords must contain at least 12 Unicode code points and at most 256 UTF-8 bytes. The provisioning workflow, secure password setup, proof collection, evidence retention, and authorization for role assignment are **not implemented**. `admin` sessions are possible only for existing, independently and securely provisioned admins; public signup never grants that role. An enabled account and role do not themselves establish business identity.

`POST /login` takes JSON `{ "email": "…", "password": "…" }` and returns `{ token, token_type: "Bearer", expires_in: 900 }` on success. Email is a conservative ASCII identifier, lowercased and trimmed; it is not proof of identity. Wrong password, unknown account, disabled account and disallowed role receive generic invalid-credential responses (input shape errors receive 400). Request bodies are capped at 8 KiB. Protect login and all auth routes with independently operated, fail-closed distributed IP/account rate limits, abuse monitoring, reasonable request and concurrency limits, and secure, privacy-preserving audit logs **before mounting**; this module does not supply a distributed limiter and scrypt is deliberately resource intensive. Responses alone do not guarantee timing-indistinguishability. No password change, account recovery, email verification delivery, MFA/2FA, trusted admin provisioning, session inventory, key rotation, anomaly detection or user-facing security notifications are implemented. Do not claim otherwise. Use an independently reviewed lifecycle plan before release.

Changing a user's role or legacy password, or changing v2 account credentials, verification fields, email or enabled state, permanently revokes existing sessions via DB triggers. Deleting/recreating a v2 account also revokes old sessions. These triggers do not stop a new session from being issued with an unchanged password after a logout or a later re-enable. To handle compromise, disable the account or replace credentials through a separately audited process; protect DB writes and trigger privileges. The database account table and session table are highly sensitive and must not be writable by untrusted principals. Audit privileged provisioning, role updates and trigger changes externally. Expired/revoked sessions require an approved retention and safe cleanup policy. A signing-key compromise requires an incident runbook, revoking all sessions and coordinated key replacement; no key-ring or graceful rotation implementation is provided. Every consent service instance and verifier must also be shut down or switched to the new key on compromise.

## Migration and operations

`migrateAuthV2V1` in `server/src/db/migrations/003_auth_v2.ts` is an explicit function, not a CLI or startup hook. It requires an exclusively checked-out `pg.Client` or `PoolClient` with no enclosing transaction and a trusted, selected schema in its search path. It uses its own transaction, advisory lock and independent `auth_v2_schema_migrations` checksum ledger. Unknown/modified history fails closed; an applied matching version is a no-op. Never edit an applied migration; create a reviewed forward migration. The migration expects `users(id TEXT PRIMARY KEY, role, password_hash)` and creates `auth_v2_accounts`, `auth_v2_sessions`, indexes and triggers on `users` and the account table. Triggers update session rows on user role or legacy password changes, so role/password writers need the required privileges; an error will fail their transaction. Check interactions with all existing triggers, permissions, lock ordering, deadlock retries, and production schema drift. User role changes can also fire `gc_sub` triggers if that separate migration exists. Restrict ability to bypass or disable triggers.

No auto migration, production database access, deployment or maintenance change has occurred. Before a separately authorized run, keep maintenance on, stop writers, backup and rehearse restoration, inspect the real schema and privileges, test on a sanitized clone, obtain independent security/privacy review, and plan locking, migration verification and rollback/forward repair. Do not delete existing users or source data. A checksum does not detect out-of-band schema drift. Configure trusted search paths and protect schema creation; avoid writable schemas earlier in the path. Run any schema operation only after explicit approval.

## Tests

Unit tests require no database:

```sh
node --experimental-strip-types --test server/test/auth-v2-unit.test.ts
```

Integration tests require an **explicitly disposable local PostgreSQL 16 cluster**, never a real/shared database. They accept only an explicit `127.0.0.1:port` URL with database name `auth_v2_test_*` and no URL options, create/drop a random schema, and use synthetic users, data and RSA keys. URL validation alone cannot establish disposability. The caller must ensure an isolated cluster and clear dangerous `PG*` environment settings. For an already-started disposable cluster and empty test database:

```sh
AUTH_V2_TEST_PG_URL=postgresql://ubuntu@127.0.0.1:55491/auth_v2_test_disposable \
  node --experimental-strip-types --test server/test/auth-v2-pg.test.ts
```

Tests cover migration rollback/idempotence/tampering, public admin rejection and no mapping, password and key validation, strict signed-token validation even with a matching session row, verified account gates, live roles, DB session hashes, logout and logout-all concurrency, disable/re-enable, delete/recreate, password/role change revocation, expiry, generic errors and real consent-service compatibility. Direct consent-service calls reject a logged-out JWT; `gc-sub-auth-races.test.ts` exercises all consent operations against invalid sessions and both lock orderings of logout, logout-all, disable and role changes, plus expiry and statement-snapshot boundaries. Representative minimal schemas are not a substitute for migration rehearsal on a sanitized clone or independent review.
