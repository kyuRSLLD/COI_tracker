# Self-reported private COI files — isolated prototype

**Not deployed or wired into startup.** This is a separate, default-off service and manual forward migration. The composable HTTP router can be mounted by the synthetic-only opt-in and by an explicit opt-in in the new [unmounted production-intended composition](./secure-v2-production-composition.md), which also injects the S3 adapter. Neither composition establishes production readiness; see [PRIVATE_FILE_S3_ADAPTER.md](PRIVATE_FILE_S3_ADAPTER.md). There is no multipart handler, production app/bootstrap import, default S3 client, AWS call at construction, cloud credential, presigned URL, public download, or production migration invocation. Existing legacy certificate storage/routes and their security properties are unchanged. This prototype does not make them safe. Fresh-profile fixture evidence is synthetic and must never be used as production provisioning.

## Authority and consent

A currently signed-in, enabled, verified auth-v2 `sub` with one active fresh-email-control profile can upload a new file attached to one of that profile's immutable self-reported COI metadata records. Fresh-email-control evidence verifies neither the user's company/authority nor the insurance/document. The upload returns only a generated file UUID, never the storage key, version, digest, or legacy mapping. Metadata sharing and profile connection **do not share files**. A separate affirmative `FILE_CONSENT_V1` grant names both the exact file UUID and one currently connected, eligible `gc` user. A future replacement, identical-byte upload, another COI, another GC, or a client/admin gets nothing automatically. `grant` is idempotent for an active grant; revocation is permanent for that grant row. A new affirmative consent creates a new row.

`download` is GC-only (the separate `downloadOwn` is owner-only) and requires live auth-v2 RS256 credentials, an unexpired/unrevoked DB session, role and enabled/verified account, fresh active owner profile with valid sub role/account, a current profile-only v2 parent connection and that file's active grant. Connection revoke/replacement, profile revocation, role change and account disable/delete end affected file grants; restoring the parent, role or account never resurrects child grants. Grant events are append-only. File grants are independent of metadata grants. All ordinary service failures surface only `Unavailable`; callers must avoid logging exceptions, private IDs, bytes, keys and scanner diagnostics. The owner may list ready files and download their own bytes; the GC list contains only files with a current individual file grant and active parent/profile. Admins and clients cannot use either surface.

The service rechecks the real auth-v2 JWT and session itself, not a request-supplied user ID or role. Database locks are acquired in the order sorted users, sorted accounts, caller session, profile, parent connection, child grant. Final session/expiry validation happens before commit. Download buffers and checks the whole object while holding those authorization locks. Role/connection/grant changes serialize with the authorization decision; these locks can reduce throughput and slow revoke during a slow storage read. Once an authorized operation commits and hands bytes to its caller, revocation cannot recall already delivered bytes. The router buffers the entire authorized result before sending it; it does not claim that an HTTP response already started can be recalled. Its trusted storage adapter must itself enforce the supplied maximum while reading, before buffering, and reject redirects or unapproved network destinations. The service cannot enforce an adapter's internal memory behavior.

## Inspection and storage trust boundary

Both adapters are **required** injected server-owned dependencies; absence fails construction. No default or fallback adapters are provided. `inspect(bytes,mime)` must apply the reviewed parser and scanner checks to exactly those PDF/JPEG/PNG/WebP bytes and fail on rejected or unsupported input, malware, scan/parser failure, incomplete scans, unavailability and timeouts. No parser can prove all malformed or malicious files are rejected. A result's MIME, size and lower-case SHA-256 must match the service's own digest. An untrusted adapter can lie; this interface is not itself a malware scanner or evidence of safety. Production must independently review and isolate the real parser/scanner worker, use a maintained scanner/signatures and enforce resource, network, filesystem, process and privilege isolation. Even successful scanning does not prove a document safe, sanitize it, or verify its contents.

The service makes its own byte snapshot synchronously before its first await and computes its own SHA-256 and size. It supplies separate copies to the inspector and storage, and checks both inspection evidence and write receipt against the snapshot. It allocates an unpredictable server-only key and file UUID, never accepting keys, file metadata, digest, object versions, or profile IDs from the caller. `putNew` must use a private write-once namespace, atomically reject overwrite, and return a nonempty immutable version identifying exactly the committed object and a genuine size/digest/MIME receipt. Literal S3 `null` version IDs are rejected. An adapter must not synthesize proof by echoing unchecked caller metadata. `getVersion` must read exactly the requested key/version. The service checks returned version, size, and the SHA-256 of its private read snapshot before releasing any bytes. The server remains the only access path: block all direct/public/bucket/ACL/presigned URL or legacy access to the namespace. A version ID by itself does not prove immutability; trusted storage, overwrite/deletion controls and privileges are mandatory.

Uploads are bounded at 10 MiB, or a lower trusted configured maximum. The route bounds the incoming stream and applies an absolute deadline through inspection and storage; the adapters receive an abort signal and must honor it. The service checks cancellation before/after external calls and before transaction commit. A deadline cannot undo an already in-flight storage or database commit: the outcome can be ambiguous and orphan reconciliation is mandatory. Hung/uncooperative adapters may continue consuming resources; require adapter-level timeouts, cancellation, concurrency and admission controls. This service holds several copies in memory. Downloads are fully buffered before response with a fixed attachment filename, `nosniff` and no-store. No streaming or public storage URL is used.

## Non-atomic writes and reconciliation

1. A committed `pending` reservation, containing the private allocated key, byte metadata and COI/profile binding, is inserted under valid owner authorization **before** inspection or storage. Pending rows are never downloadable or grantable.
2. Inspection must succeed before a write is attempted. Any adapter failure, malformed result, unverifiable receipt, absent/nonbinding version, or later reauthorization failure returns a generic error. A best-effort update marks the reservation `orphan`. A crash, lost connection, ambiguous commit/write, or failure of that update leaves a durable `pending` row. These are reconciliation candidates, not downloads. A storage object written before a failure remains private and inaccessible through the service. Promotion to `ready` occurs only after successful inspection and a bound storage receipt, in a separate owner/session/profile-revalidated database transaction. There is no atomic S3/database transaction.
3. Operators must build a separately reviewed, privileged reconciliation/retention process. It must distinguish live in-flight uploads from abandoned work using a conservative lease/deadline and process state before taking action; these fields/worker are **not implemented** here. Inspect aged `pending` and `orphan` rows, privately enumerate exact versions at the allocated key, and remove or retain according to approved policy. Never blindly promote candidates, infer safety from metadata, expose keys, or delete a version referenced by a ready record. Treat uncertain outcomes as private and retry safely. Alert on stranded/orphan objects and track deletion completion separately. Ready rows and grants/events are immutable history; deletion/retention, legal holds, quotas and GC are not implemented.

The service assumes trusted DB/schema administrators and least-privileged application/database accounts. Restrict direct SQL writes, schema changes, and storage access; a DB admin or dishonest adapter can bypass service guarantees. Migration checksums detect changed migration history, not schema tampering. Independent security review and tests of actual privileges, infrastructure and operational failure modes are required before any production integration.

## Manual migration

On a dedicated idle PostgreSQL connection and only after review/backups, explicitly call `migrateSelfReportedPrivateFilesV1(client)` exported from `server/src/db/migrations/007_self_reported_private_files.ts`. It starts its own transaction and checks exact pinned migration histories for GC/sub, auth-v2, registration, fresh profile evidence and the copied metadata migration (`006_self_reported_coi_metadata.ts`). It applies its own ledger/checksum; a repeat returns `already-applied`; unknown/missing histories fail closed. No automatic runner, backfill, down migration, legacy mapping, or production database access is included. Migration advisory locking does not replace exclusive operational migration coordination. Test fixture helpers must never be used to backfill existing users or production profiles.

## Synthetic HTTP contract and rate limits

The detached router is `server/src/routes/selfReportedPrivateFilesV2.ts`, opt-in via `unsafeTestOnlyPrivateFiles` in `createSecureV2SyntheticTestApp` or separately through the unmounted production-intended factory's explicit configuration. There is no production startup wiring. Under `/api/v2/self-reported-private-files`, `GET /consent` returns the exact file disclosure; `PUT /own/:coiId` accepts raw PDF/JPEG/PNG/WebP bytes, `GET /own/:fileId` reads an owner's ready file; `GET /own/list` and `GET /granted/list` return up to 100 files, with `nextCursor`. To continue, POST to the same list endpoint with JSON `{"after":"<nextCursor>"}`. IDs are opaque; listings contain only file ID, COI ID, MIME, size, creation time and `self_reported_unverified`, not storage keys, digests or storage versions. Concurrent grants/revokes can change later pages; a cursor is not a snapshot. `POST /grant` requires exactly `{fileId,gcUserId,consentVersion,affirmative:true}` using the returned version, and `POST /revoke` requires exactly `{fileId,gcUserId}`. `GET /granted/:fileId` is GC-only. No query strings are accepted. File consent is distinct from profile and metadata consent, and every file and GC needs a separate grant. Repeating an active grant is idempotent; repeating an upload creates a distinct file.

The router requires a server-owned authenticator that establishes a freshly verified `authV2` credential and a shared atomic fail-closed limiter. The service independently re-verifies that credential and live session. The supplied test callback is **not** such a limiter. `privateFilesRateLimiter.ts` provides an optional atomic PostgreSQL fixed-window adapter and an explicitly invoked separate migration, neither mounted nor run at startup. All application instances must use the same authoritative database and identical budgets/window; direct callers must not bypass the router. Denial, timeout or failure is closed; the limiter receives only the TCP peer address or verified subject, never proxy headers or credentials. Behind a proxy the peer is the proxy, not an automatically trusted client IP. Hashed bucket identifiers are pseudonymous, not anonymous. Before real use, review policy, privacy, retention and concurrency, plus safe cleanup of expired buckets and database growth from many distinct identities. Fixed windows, proxy aggregation, DB outages and limit timing can affect availability; limiter callbacks that ignore deadlines are not canceled.

No trust boundary can verify an injected inspector, limiter, or storage implementation is honest. Synthetic fixtures, mock malware/transport/limiter outcomes, and disposable PostgreSQL cannot verify production scanning, immutable storage, isolation, quotas, redirect/SSRF defenses, ingress limits, operational monitoring, legal retention, deployment or identity/insurance claims. Review all such components and complete threat, race and infrastructure testing before any production integration.
