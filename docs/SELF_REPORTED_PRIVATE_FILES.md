# Self-reported private COI files — isolated prototype

**Not deployed or wired.** This is a separate, default-off service and manual forward migration. There is no HTTP router, multipart handler, app/bootstrap import, S3 implementation, AWS call, cloud credential, presigned URL, public download, or production migration invocation. Existing legacy certificate storage/routes and their security properties are unchanged. This prototype does not make them safe. The synthetic suite composes the metadata and file services only in tests; fresh-profile fixture evidence is synthetic and must never be used as production provisioning.

## Authority and consent

A currently signed-in, enabled, verified auth-v2 `sub` with one active fresh-email-control profile can upload a new file attached to one of that profile's immutable self-reported COI metadata records. Fresh-email-control evidence verifies neither the user's company/authority nor the insurance/document. The upload returns only a generated file UUID, never the storage key, version, digest, or legacy mapping. Metadata sharing and profile connection **do not share files**. A separate affirmative `FILE_CONSENT_V1` grant names both the exact file UUID and one currently connected, eligible `gc` user. A future replacement, identical-byte upload, another COI, another GC, or a client/admin gets nothing automatically. `grant` is idempotent for an active grant; revocation is permanent for that grant row. A new affirmative consent creates a new row.

`download` is GC-only and requires live auth-v2 RS256 credentials, an unexpired/unrevoked DB session, role and enabled/verified account, fresh active owner profile with valid sub role/account, a current profile-only v2 parent connection and that file's active grant. Connection revoke/replacement, profile revocation, role change and account disable/delete end affected file grants; restoring the parent, role or account never resurrects child grants. Grant events are append-only. File grants are independent of metadata grants. All ordinary service failures surface only `Unavailable`; callers must avoid logging exceptions, private IDs, bytes, keys and scanner diagnostics. No listing API or route is included.

The service rechecks the real auth-v2 JWT and session itself, not a request-supplied user ID or role. Database locks are acquired in the order sorted users, sorted accounts, caller session, profile, parent connection, child grant. Final session/expiry validation happens before commit. Download buffers and checks the whole object while holding those authorization locks. Role/connection/grant changes serialize with the authorization decision; these locks can reduce throughput and slow revoke during a slow storage read. Once an authorized operation commits and hands bytes to its caller, revocation cannot recall already delivered bytes. In particular, a future HTTP streaming implementation can race with revocation after authorization and requires separate policy/design; this prototype has **no streaming revocation guarantee**.

## Inspection and storage trust boundary

Both adapters are **required** injected server-owned dependencies; absence fails construction. No default or fallback adapters are provided. `inspect(bytes,mime)` must apply the reviewed parser and scanner checks to exactly those PDF/JPEG/PNG/WebP bytes and fail on rejected or unsupported input, malware, scan/parser failure, incomplete scans, unavailability and timeouts. No parser can prove all malformed or malicious files are rejected. A result's MIME, size and lower-case SHA-256 must match the service's own digest. An untrusted adapter can lie; this interface is not itself a malware scanner or evidence of safety. Production must independently review and isolate the real parser/scanner worker, use a maintained scanner/signatures and enforce resource, network, filesystem, process and privilege isolation. Even successful scanning does not prove a document safe, sanitize it, or verify its contents.

The service makes its own byte snapshot synchronously before its first await and computes its own SHA-256 and size. It supplies separate copies to the inspector and storage, and checks both inspection evidence and write receipt against the snapshot. It allocates an unpredictable server-only key and file UUID, never accepting keys, file metadata, digest, object versions, or profile IDs from the caller. `putNew` must use a private write-once namespace, atomically reject overwrite, and return a nonempty immutable version identifying exactly the committed object and a genuine size/digest/MIME receipt. Literal S3 `null` version IDs are rejected. An adapter must not synthesize proof by echoing unchecked caller metadata. `getVersion` must read exactly the requested key/version. The service checks returned version, size, and the SHA-256 of its private read snapshot before releasing any bytes. The server remains the only access path: block all direct/public/bucket/ACL/presigned URL or legacy access to the namespace. A version ID by itself does not prove immutability; trusted storage, overwrite/deletion controls and privileges are mandatory.

Uploads are bounded at 10 MiB, or a lower trusted configured maximum. Integration must limit input while receiving it, before allocating a buffer, and enforce request limits, deadlines, concurrency, quotas and admission control. This service can hold several copies in memory; it does not enforce those upstream controls. Production download handling must set safe attachment/content-disposition and `nosniff`, prevent caching and unsafe inline rendering, use generic errors and require authorization on every request. No route or browser behavior is provided here.

## Non-atomic writes and reconciliation

1. A committed `pending` reservation, containing the private allocated key, byte metadata and COI/profile binding, is inserted under valid owner authorization **before** inspection or storage. Pending rows are never downloadable or grantable.
2. Inspection must succeed before a write is attempted. Any adapter failure, malformed result, unverifiable receipt, absent/nonbinding version, or later reauthorization failure returns a generic error. A best-effort update marks the reservation `orphan`. A crash, lost connection, ambiguous commit/write, or failure of that update leaves a durable `pending` row. These are reconciliation candidates, not downloads. A storage object written before a failure remains private and inaccessible through the service. Promotion to `ready` occurs only after successful inspection and a bound storage receipt, in a separate owner/session/profile-revalidated database transaction. There is no atomic S3/database transaction.
3. Operators must build a separately reviewed, privileged reconciliation/retention process. It must distinguish live in-flight uploads from abandoned work using a conservative lease/deadline and process state before taking action; these fields/worker are **not implemented** here. Inspect aged `pending` and `orphan` rows, privately enumerate exact versions at the allocated key, and remove or retain according to approved policy. Never blindly promote candidates, infer safety from metadata, expose keys, or delete a version referenced by a ready record. Treat uncertain outcomes as private and retry safely. Alert on stranded/orphan objects and track deletion completion separately. Ready rows and grants/events are immutable history; deletion/retention, legal holds, quotas and GC are not implemented.

The service assumes trusted DB/schema administrators and least-privileged application/database accounts. Restrict direct SQL writes, schema changes, and storage access; a DB admin or dishonest adapter can bypass service guarantees. Migration checksums detect changed migration history, not schema tampering. Independent security review and tests of actual privileges, infrastructure and operational failure modes are required before any production integration.

## Manual migration

On a dedicated idle PostgreSQL connection and only after review/backups, explicitly call `migrateSelfReportedPrivateFilesV1(client)` exported from `server/src/db/migrations/007_self_reported_private_files.ts`. It starts its own transaction and checks exact pinned migration histories for GC/sub, auth-v2, registration, fresh profile evidence and the copied metadata migration (`006_self_reported_coi_metadata.ts`). It applies its own ledger/checksum; a repeat returns `already-applied`; unknown/missing histories fail closed. No automatic runner, backfill, down migration, legacy mapping, or production database access is included. Migration advisory locking does not replace exclusive operational migration coordination. Test fixture helpers must never be used to backfill existing users or production profiles.

## Local synthetic verification
Both `scripts/test-fresh-sub-registration.sh` and `scripts/test-self-reported-private-files.sh` use disposable loopback-only PostgreSQL 16 and synthetic accounts. The combined test applies both independent 006 migrations and `007_self_reported_private_files.ts` in one synthetic schema; the file-service test separately exercises the 007 prerequisites and grant behavior. No migration is run on a production database. Ledger versions are each **1** even though filenames contain 006 or 007; the ledgers are separate. The metadata DDL digest is `d1f39e09e5f9e718154ed344e52535916c281caa52c9b0c1c93e22d6c0be8567`, matching 007's pin. The metadata advisory-lock change is outside the hashed DDL. Metadata 006 and file 007 both use advisory key `(1129273683, 7)`, so they serialize; anonymous reporting 006 uses key `(1129273683, 6)`. These locks do not replace exclusive operational migration coordination.

The file test exercises affirmative file consent, metadata-only denial, other GC/client denial, unauthorized revocation, exact byte snapshots, scan/evidence/receipt/read failures, orphan tracking, revoke/disconnect/reconnect, role/account loss and regrant, session expiry, and lock races. Its base cases use mock inspection and synthetic labels, not validated real documents. When `PRIVATE_INSPECTION_TEST_PYTHON` names the absolute path to the isolated Python environment, an additional test connects the real `privateFileInspection.ts` parser through a contract-conforming adapter, a local Unix-socket mock ClamAV, and in-memory write-once/versioned storage. It uploads a synthetic valid PNG, confirms exact scanned/stored bytes and separate consent, and checks malformed input and mock malware fail before storage. If the variable is absent, that subtest is explicitly skipped. The local scanner suite separately covers synthetic PDF, JPEG, PNG and WebP fixtures; the composed file-service test currently exercises PNG only.

Example from the repository root:
```sh
PRIVATE_INSPECTION_TEST_PYTHON="$PWD/.work/inspection-venv/bin/python" bash scripts/test-fresh-sub-registration.sh
PRIVATE_INSPECTION_TEST_PYTHON="$PWD/.work/inspection-venv/bin/python" bash scripts/test-self-reported-private-files.sh
```

These tests use no real AWS, clamd, production data or HTTP file route. A mock scanner cannot validate ClamAV detection or configuration, and in-memory storage cannot validate S3 immutability, permissions, versioning or operational failures. Passing tests do not establish identity, insurance, safety, deployment readiness or production access controls. The real scanner/worker are not packaged into the application build.
