# GC–sub connection-only pilot bootstrap — not deployment approval

`server/src/pilot-entry.ts` is a separate listener using `createPilot` and `createSecureV2ProductionApp`. It is **not** referenced by the current package scripts, Dockerfile, Railway configuration, or legacy listener. No changes here migrate a database, deploy a service, provision AWS, switch off maintenance, or make any existing endpoint safe. The current Dockerfile builds/starts the legacy entry and does not copy the TypeScript sources into its runtime image. Running it unchanged is **not** this pilot. A separately approved, reviewed build/start and health configuration is necessary, with no legacy process or legacy routing in the same exposed service.

## Surface and controls

Only exact URLs without queries are allowed: `/healthz`, `/api/v2/auth/{login,logout,logout-all,me,register/request,register/confirm}`, and `/api/v2/connections/{consent,profile,general-contractors,qr,qr/redeem,revoke,subcontractors}`. Other paths, including GC owner, COI listing, invitations, metadata, files, uploads and legacy routes, are 404 before the inner app. Exact route matching does not make arbitrary methods valid. The composed invitation-recipient callback always returns false. The metadata/files switches must both be `disabled`; no S3 or scanner is constructed. No UI, CORS policy, file handling, or invitation delivery is provided. Health is liveness only, not readiness.

Registration requests are limited to the exact configured mailboxes before challenge creation; the SES delivery policy checks again. Confirmation looks up the submitted token hash and permits only an unexpired delivered, unused challenge whose stored email is in this process's mailbox list, then lets the existing registration transaction perform its own checks. Lists must be identical on all replicas, and removing a mailbox requires draining/restarting **all** old replicas; otherwise an old replica can still accept it. Use a new isolated database with no unexpected writers or previously armed challenges; the preliminary check and the existing confirmation transaction are separate, so database authorization must prevent a challenge's email being changed between them. Email control does not establish business or insurance ownership. The connection flow and consent/role rules still require independent end-to-end security review.

All allowed non-health requests first pass a database-backed global and socket-peer front gate. Before login is processed, another gate normalizes the account identifier exactly like the current auth handler and applies global/peer/account budgets. This front-door control is independent of any optional account-throttle hook in the underlying auth implementation; changes to parsing or normalization in that handler require review of this wrapper. Registration is also limited by action, peer and hashed identity; protected and connection router callbacks each have global/peer/principal or global/peer budgets. See `pilot-limiter.ts` for the concrete per-minute constants, including caps for disabled router scopes. Every call is one PostgreSQL atomic statement, committing before allow; denied attempts consume global capacity. Fixed windows permit a burst up to twice the nominal limit at a window boundary. A process-local maximum of 64 outstanding limiter queries protects each pool, not the whole fleet. Database errors, missing/mismatched config, timeouts and saturation deny, including uncertain commits; there is no permissive fallback or retry. Every decision checks an administrator-owned shared key fingerprint, preventing differently configured replicas from silently using separate counters.

The peer comes from `req.socket.remoteAddress`, **not** forwarded headers. Behind Railway this can identify a proxy rather than an end user; all users can share the same peer budget and different proxies can distribute it. It is deliberately not represented as verified client IP. This can cause denial of service and is insufficient alone for fair client attribution or all abuse protection. Before any exposure, establish a reviewed, exclusive, trusted-proxy/client-IP and ingress abuse-control architecture, global request/body/connection/concurrency limits, TLS and direct-origin prevention. This source cannot ensure those infrastructure properties. Rate caps are conservative examples, not capacity-tested production policy. Shared anonymous requests can exhaust a global window; account limits can be deliberately exhausted to deny a victim. Bucket key HMACs are pseudonymous, not anonymous; protect the key and database and do not log hashes.

Each query deletes up to 10 entries older than two database-clock minutes before inserting at most three fresh entries; normal successful decisions therefore outpace their own old-row accumulation. Low traffic may leave old rows until further traffic; clock jumps, database failures, restarts, and operator actions can affect cleanup and windows. Monitor disk space, write amplification, query latency, deadlocks and storage retention with aggregate metrics only. Database failover clocks must be synchronized and tested. Protect the config table from the app role; a compromised database writer/owner can defeat any database limiter. Limit table writes and SQL logs; never record raw parameters, bodies, URLs with tokens, authorization headers, addresses, email, HMAC digests, codes, credentials or provider errors in app, proxy, PostgreSQL, AWS, tracing or crash logs.

## Subcontractor profile access and disconnect

`GET /api/v2/connections/general-contractors` is available only to a currently authenticated, enabled, email-verified subcontractor with one active fresh-email-control profile. The profile is derived from the credential, not supplied by the caller. It returns `{ "generalContractors": [{ "gc_user_id": "…", "gc_name": "… or null" }] }`: only IDs and self-reported names of currently eligible GC-role accounts with an active profile-only V2 grant. This is not an identity or business verification. The endpoint does not return COI, file, contact, sub, or client data; it does not open the metadata endpoint. Names can be duplicate or absent; use the account ID to disambiguate. More than 500 eligible accounts fails closed with 503 rather than returning an incomplete list. The list is a point-in-time view, not a continuously synchronized authority; role, account and connection changes can race with reads.

The sub selects an account, reviews its name and ID, and explicitly confirms `POST /api/v2/connections/revoke` with `{ "profileId": "…", "gcUserId": "…" }`. The existing transaction independently verifies the live sub session and profile ownership, serializes on the profile, revokes the matching grant and records its event, and invalidates all unspent profile QR codes and pending invitations for that GC. Installed child-grant triggers revoke affected separate metadata/file grants in the same transaction; this pilot does not enable those routes. The request is idempotent and 204 is generic. Cross-owner requests fail generically, and response errors do not reveal target existence. A failed or lost response may have committed: the UI hides any previously displayed QR and refreshes the list, reports uncertainty, and requires another explicit decision; a refresh can itself fail or race a still-running request. Previously received or already-authorized in-flight data cannot be recalled. A later new affirmative connection can grant access again. QR issuance and disconnect operations in this UI are mutually exclusive; another session or server-side actor can still race under the transaction ordering described above.

## Strict settings

Supply the following explicitly via a trusted secret/config provider. No `.env`, database URL, legacy defaults, test delivery, or runtime dependency injection is used. Errors are deliberately generic. Do not print values or put secrets in build artifacts, shell history or command-line arguments.

* `SECURE_V2_CONFIG_VERSION=1`; `SECURE_V2_METADATA=disabled`; `SECURE_V2_FILES=disabled`.
* `SECURE_V2_DB_HOST`, `SECURE_V2_DB_PORT`, `SECURE_V2_DB_NAME`, `SECURE_V2_DB_USER`, `SECURE_V2_DB_PASSWORD`: dedicated PostgreSQL database, DNS host, canonical positive port, least-privilege app identity. A real `pg.Pool` uses server certificate and hostname verification (`rejectUnauthorized: true`), default OS/Node CA roots or optional `PILOT_DB_CA_PEM` (an actual PEM certificate); no insecure mode. Provide a host matching the server certificate, not an unrelated proxy/IP. Pool max 10, acquisition timeout 1s, statement timeout 1.2s, lock timeout 0.4s. No PostgreSQL service is contacted during factory construction.
* `SECURE_V2_JWT_PRIVATE_KEY_PEM`, `SECURE_V2_JWT_PUBLIC_KEY_PEM`, `SECURE_V2_JWT_ISSUER`, `SECURE_V2_JWT_AUDIENCE`: distinct exact signing settings, matching RSA keys at least 2048 bits, with private PEM held only in secret storage. No legacy JWT secret.
* `SECURE_V2_SES_REGION`, `SECURE_V2_SES_FROM`, `SECURE_V2_SES_TIMEOUT_MS`: approved SES region, verified sender address and canonical timeout 100–15000 ms. A real `SESv2Client` uses the standard AWS credential provider chain, HTTPS, at most four in-flight sends, one attempt and disabled configured endpoint overrides. Provision appropriately scoped, short-lived AWS workload credentials, verify region/sender/account/sandbox recipients and test delivery separately after authorization. No sends occur at construction; SES acceptance is not proof of delivery. The AWS SDK's default credentials chain and all runtime dependencies must be secured and reviewed. Tracking is disabled by the existing adapter.
* `PILOT_REGISTRATION_MAILBOXES`: 1–20 distinct, lowercase canonical ASCII addresses separated by commas, no spaces; explicitly selected real test mailboxes. Never use a whole domain or wildcard. They are private configuration and must be the same on every replica.
* `PILOT_LIMITER_HMAC_KEY`: a cryptographically random 32-byte secret encoded as canonical unpadded base64url; same value on every replica. Generate and store through a secret manager, not a shell command in history. This and the config fingerprint must be provisioned consistently, and key rotation requires a coordinated outage/drain and atomic configuration update; changing it resets all budgets. Treat the fingerprint as sensitive.
* `PORT`: explicit canonical positive decimal port 1–65535 at startup. Node process flags and TLS trust overrides are not supported: `NODE_OPTIONS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, and `AWS_CA_BUNDLE` must be absent. Do not add custom endpoint/proxy/SDK instrumentation that logs secrets or bypasses TLS. Review the process launch environment, DNS, CA trust and credential-provider settings.

## Manual database preparation — NOT performed here

After separately authorized schema review, provision a fresh, isolated PostgreSQL database and the existing reviewed owner/auth/consent/registration/fresh-profile prerequisites in the correct compatible order. The SQL file `server/src/pilot-limiter-schema.sql` is a separate manually applied schema, not an automatic migration; it must be applied once by an administrator, not blindly replayed or applied by the app. Do not point it at production or a legacy/shared database. Its app role needs only `SELECT, INSERT, UPDATE, DELETE` on `public.pilot_rate_buckets_v1` and `SELECT` on `public.pilot_rate_config_v1`; it must not own, alter or write the latter. Grant other existing app-table permissions separately and minimally, prohibit untrusted DB writers, restrict search path and protect SQL/audit logging.

Provision exactly one config row, with `singleton=true` and `key_check` as the 32-byte result of `pilotLimiterKeyCheck(Buffer.from(PILOT_LIMITER_HMAC_KEY, 'base64url'))` exported from `server/src/pilot-limiter.ts`. In a reviewed admin tool, use a **parameterized** `INSERT INTO public.pilot_rate_config_v1(singleton,key_check) VALUES (true,$1)` with the binary result as `$1`. Do not interpolate or print the secret or fingerprint. The app checks this row and table connectivity before listening and checks the fingerprint on every limiter decision. This is not a complete schema/permission/readiness validation. A database outage after startup denies traffic; liveness may still return 200. Backup, privilege, integrity, cleanup, restore, secret rotation and rollback procedures require separate rehearsal.

## Verification and run instructions

Node 22+ and existing workspace dependencies are needed. `./scripts/test-profile-connections.sh` creates and destroys a new loopback-only PostgreSQL 16 cluster, then exercises the connection HTTP router and existing consent service tests; it needs local PostgreSQL 16 binaries and must run as a non-root user. `python3 client/tests/v2-connection-only/test_connection_only.py` runs a loopback Vite host and Playwright/Chromium with intercepted synthetic requests, including the disconnect UI and ambiguous/timeout behavior. They do not prove the pilot ingress, real browser-to-database integration, actual deployment, or data already in flight. With reviewed dependencies available, type-check without changing config:

```sh
./node_modules/.bin/tsc --noEmit --target ES2022 --module NodeNext --moduleResolution NodeNext --strict --esModuleInterop --skipLibCheck --allowImportingTsExtensions server/src/pilot-bootstrap.ts server/src/pilot-entry.ts server/src/pilot-limiter.ts server/test/pilot-bootstrap.test.ts
env -u NODE_OPTIONS node --experimental-strip-types --test server/test/pilot-bootstrap.test.ts
```

The last command skips the PostgreSQL tests unless explicitly enabled against an independently prepared **disposable local** cluster on port 55432 with the pilot schema and role `ubuntu`. Set `PILOT_TEST_PG_SOCKET` to its `/tmp/pilot-pg-*/socket` and, only when localhost TLS is separately configured with a disposable trusted certificate, `PILOT_TEST_TLS_CA` to its `/tmp/pilot-pg-*/data/server.crt`. The tests insert a config fingerprint, create and **drop `public.auth_v2_registration_challenges`**, truncate pilot tables, and **drop both pilot limiter tables**. Never run these tests against a shared, persistent, remote, production or valuable database; verify the socket and localhost port are exclusively the disposable cluster. The local SQL test exercises concurrent calls from two limiter instances, and the TLS test checks that an untrusted certificate is rejected and confirms the mailbox gate, without contacting SES. They do not prove production topology or failures. The bootstrap unit tests use ephemeral RSA keys and no SES transport calls; no AWS or Railway was contacted.

Only after all reviews, isolation, manual preparation and authorization, a controlled source checkout with dependencies and trusted environment could run `node --experimental-strip-types server/src/pilot-entry.ts`. This is not a recommendation to expose it. For an actual Railway build, separately review a build artifact and start command targeting the new entry, dependency lockfile, CA trust, secret/credential injection, sole ingress, and `/healthz` liveness behavior. Never leave the current `node server/dist/index.js` Railway command pointing to the legacy app. No deployment change is included here.

## Remaining release blockers

Independent security review and realistic isolated end-to-end tests (including concurrent/retry/timeout/failover behavior, approved recipient registration, login, QR consent/revoke and cross-tenant authorization); correct underlying schema and least privilege; verified TLS against the real database; SES identity, account/sandbox, IAM and verified real mailbox testing; authenticated trusted ingress and distributed abuse controls; safe observability and incident response; secret/credential rotation; persistence, cleanup, retention, backup/restore/rollback; reviewed readiness; UI integration and same-origin/CORS/CSRF design; and a reviewed, explicit deployment/build cutover with no alternative legacy route. This pilot is not audited, tested against AWS or Railway, or authorized for exposure.
