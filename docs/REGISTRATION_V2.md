# Disconnected v2 registration: review only

This module is **not mounted, deployed, or connected to a real provider**. It is not yet approved for release. `server/src/v2/auth.ts` and `003_auth_v2.ts` are exact copies of the separately developed auth v2 files. Its `/register` placeholder remains unchanged; login and its existing contracts are unchanged. The separate `createV2Registration(pool, { delivery, rateLimiter })` router offers `POST /register/request` and `POST /register/confirm`. A future reviewed composition may mount both routers at the same prefix, with separate exact paths. This document is not an instruction to mount them now.

## Contract and security boundary

* Request takes only `{email}`. It never accepts a password, role, profile ID, delivery endpoint, or provider choice. It returns a generic 202, including for an existing account, and sends the same kind of challenge to the normalized address. There is no account, user, or profile until confirmation. There is no public admin registration.
* The email recipient enters the 256-bit random base64url token and **chooses** `{role: 'gc' | 'sub', password, first_name, last_name, phone}` at confirmation; sub additionally supplies `{company_name, trade}`. A single `name` field is not accepted. Both names are required, nonempty after trimming, at most 100 UTF-16 code units each before trimming, well-formed Unicode, and cannot contain ASCII control characters. Stored `users.name` and new sub's `contact_person` are the trimmed first and last names joined by one space; the two names are also stored separately. An initiator cannot set a victim's password or contact/business/profile details in advance. Confirmation returns the same generic 200 for success, already used, expired, and existing account; an HTTP 200 is **not proof** that an account was created. User subsequently uses existing v2 login. Invalid shape/role receives generic 400; unavailable dependencies, rate denial, and operational errors receive generic 503. Responses are no-store. Timing and provider behavior are not guaranteed indistinguishable; see limitations.
* The phone must be a complete US number, at most 32 input characters, in plain digits or conventional space, dot, hyphen, and/or area-code-parenthesis formatting, optionally prefixed by `1` or `+1`. Extensions, extra digits, unsupported characters, and non-US numbers are rejected, not silently removed or truncated. `libphonenumber-js/max` validates its current numbering-plan metadata and US country classification; acceptance is not proof of assignment, reachability, ownership, or phone control, and metadata needs ongoing updates. Shared +1 numbers not classified as US by the library are rejected. The normalized national form is stored in both `users.phone` and one primary `user_phones` row. Its `mobile` label follows the existing schema convention and does not assert line type. Email verification does not verify the phone or the person's real-world identity.
* The database stores only SHA-256 of the random challenge, not the token or password. Each challenge has a 10-minute lifetime determined by PostgreSQL. It cannot be confirmed while delivery is in progress or after delivery failure. Confirmation uses a row lock and checks expiry again immediately before use, with user and phone, v2 account, new sub, owned profile, and consumption in one transaction. Different challenges racing for one email are guarded by database uniqueness. Verification references are random identifiers prefixed `email-control-only:` and contain no bearer or email.
* New source sub IDs and profile IDs are random; no preexisting sub, COI, company, or profile is found or linked by name/email. A GC gets no sub/profile/COI mappings. For sub, `auth_v2_sub_profiles` stores a separate immutable mapping with explicit email-control-only evidence; it is not a `gc_sub_profiles` mapping and cannot be used by the older consent service. It establishes control of this newly created application profile by the new user only. Neither email control nor the self-asserted company/trade demonstrates legal or independent business identity, authorization to represent a business, or COI ownership. No COIs are mapped. Existing legacy users and v2 accounts are never claimed or migrated by this flow.
* The legacy `users.password_hash` is an unusable `!v2-only!` marker; the actual credential is `hashV2Password` scrypt in `auth_v2_accounts`. Verify every legacy login/reset/import path fails safely on that marker before any integration. No session or bearer is issued by registration; v2 login remains separate.
* Server-side `delivery.sendVerification` and `rateLimiter.allow` are privileged injected dependencies. Missing, throwing or denied dependencies fail closed. The delivery adapter must actually submit to the intended mailbox and return successfully only upon provider acceptance; accepting or forging a delivery callback from a client is not verification. The module cannot prove an injected adapter is trustworthy. `allow` must return literal `true`, and must limit both routes using global and trusted client-IP controls plus per-email request limits; the `identityHash` is a digest of the normalized email for request and the token for confirm, not a substitute for global/IP limits. Do not log even the hash; email digests can be dictionary-attacked. A malicious/no-op provider or permissive limiter is an unsafe deployment configuration, not a supported mock outside tests.

## Manual schema provisioning and compatibility

The checked-in migration functions are explicit calls on an exclusively held `pg.Client`/`PoolClient`, no open transaction: apply the copied auth migration (`migrateAuthV2V1`), then `migrateRegistrationV2V1`. The tests additionally apply the existing GC/sub migration (`migrateGcSubConsentV1`) to verify isolation, but registration does not require it. Review the exact source and prerequisites first. The independently checksummed ledgers are `gc_sub_schema_migrations`, `auth_v2_schema_migrations`, and `registration_v2_schema_migrations`; they reject unexpected/changed histories. No startup hook runs any of them. A disposable test initializes the same legacy table shapes and calls the functions directly.

The registration code requires the current application schema: `users` must have writable `name`, `first_name`, `last_name`, and `phone` text columns; `user_phones` must support writable text `id`, `user_id`, `phone`, `label`, `created_at` and integer `is_primary`, as defined in `server/src/db/db.ts`. It inserts a primary row with `label='mobile'` and `is_primary=1`. Both GC and sub confirmations require this table; missing or incompatible schema/permissions/constraints cause a generic 503 and rollback rather than creating an account without contact details. These migrations do not add or verify those columns or that table. The synthetic fixture mirrors these declared shapes, not a deployed database; inspect the actual schema, grants, constraints, triggers, collations and other writers before considering integration. Nothing backfills or alters existing users/phones.

The registration migration **also alters `users`**: it adds `auth_v2_users_unambiguous_email`, requiring every existing/future email to be non-null printable ASCII without whitespace, and `auth_v2_users_normalized_email_uq`, enforcing ASCII case-insensitive uniqueness under PostgreSQL `C` collation. This prevents a concurrent legacy writer from inserting a case-variant email after the new flow checks for collisions. Existing whitespace, non-ASCII, null or case-colliding emails cause the entire migration to roll back. Legacy writers that used such values will subsequently fail. This is intentional fail-closed behavior, not a migration of or claim to those records. Independently audit data and all writers and design a reviewed remediation/compatibility plan before any migration. Account for index creation locks, disk, backup/restore, schema permissions, test rollback and runbook. Reconcile JS and database normalization, provider mailbox semantics and locale under the actual deployment environment. Any schema drift, changed constraints/triggers, partial migration history, privileged bypass, or write path that changes normalization requires a new review; do not bypass the constraint/index. The new index is not sufficient to audit arbitrary externally imported v2 accounts with inconsistent account/user emails.

Provision a restricted database role, isolation from legacy principals and end-user SQL, least privileges for the exact tables/functions, and separate migration credentials. Tables, trigger functions and ledgers must be protected from modification by untrusted callers. A safe retention process should periodically delete expired/used challenge rows using least privilege and an approved retention policy; no cleanup automation is configured. Review backups, encryption, privacy, metrics and incident response. Existing code/tests do not establish production RBAC or audit logging.

## Real email provider integration (not performed)

Implement a server-owned adapter against a vetted transactional provider. Configure verified sending domain/address and SPF, DKIM and DMARC; securely provision restricted credentials in a secret manager, TLS and certificate validation, quota/abuse/bounce monitoring, operational alerts, key rotation and provider access controls. The adapter must send the exact supplied token only to the exact supplied email, and await a definite accepted submission. Provider acceptance is not proof of inbox delivery; possession of the token establishes control of the delivered mailbox only. Timeouts or ambiguous provider results must reject; a late-delivered message may contain a nonfunctional token. Never substitute webhooks, client flags, or delivery assertions for token possession. Test real delivery separately in an approved nonproduction environment; this work uses a mock only.

Prefer a manually entered code over bearer-bearing URLs: POST the code and chosen credentials only over HTTPS. Never put the raw token in logs, analytics, traces, exception text, request capture, access logs, email click tracking, referrers, URLs, third-party page resources, browser storage, or screenshots. Disable provider link tracking and logging of message bodies; review transport and support-tool access. Do not consume on GET or automated link preview. A user-facing confirmation flow, CSRF/origin policy, domain allowlists, secure headers, content security policy and account recovery are not implemented. The provider/template must avoid claiming that company identity has been independently verified. No raw token is returned by either HTTP endpoint; it is passed to the injected delivery adapter and held briefly in server memory.

Use a highly available distributed limiter with atomic shared state, global/request-IP/per-email quotas, sensible time windows and anti-abuse monitoring, plus IP/global limits for confirmation, and secure reverse-proxy trust configuration so arbitrary forwarded headers cannot spoof `req.ip`. Rate limit login independently: this work does **not** modify the copied v2 login and that module does not implement an injected login limiter. Set limits to handle expensive scrypt and prevent storage/email floods. 503 on limiter failure is intentional. Address mailbox enumeration and timing side channels through threat review and provider behavior; the uniform response/body alone is not a formal constant-time guarantee.

## Release blockers

1. **Consent identity mismatch:** `gc_sub_profiles.verified_at`/`verification_reference` in the existing `gcSubConsentService` is documented as independently verified business/profile ownership. This module instead creates a separate `auth_v2_sub_profiles` email-control-only record; the old service cannot use it. Do **not** copy or promote it to `gc_sub_profiles` based only on email. First implement and test an explicit separately audited business-identity gating/transition model across all profile consumers, including reads, grants, revocation and role changes, or approve a deliberate product/security change to the evidence contract. A prefix alone is not enforcement. Registration/login are not end-to-end GC/sub consent or sharing.
2. Security review and end-to-end authorization integration are outstanding. In particular, the existing GC/sub service's token verification must be composed behind the v2 live-session `requireAuth` middleware, not used as a standalone authorization mechanism. The legacy app has separate auth/routes, which have not been retired or made safe by this disconnected work.
3. Supply and independently test a real trusted provider and production-grade distributed abuse controls. Review registration pre-hijacking, user interface/token handling, delivery retries, timing, privacy and login throttling.
4. Audit and remediate legacy data/write compatibility before any migration; review DB privileges, transactional behavior and isolated namespace/ledger requirements. The index and check intentionally affect the shared `users` table.
5. Establish account recovery, email-change/reverification, account disable/delete, challenge cleanup, audit events and incident/operational procedures. Present code does not implement them. Audit events do not establish real-world identity. There is no real-provider, integration deployment, S3, production-data, load, failover, external security, or email-deliverability test in this work.

## Local disposable PostgreSQL 16 test

Only use a disposable loopback database whose name matches `registration_test_*`. With PostgreSQL 16 tools installed and a free port, one example (trust authentication is **test-only**):

```sh
mkdir -p "$PWD/.work/reg-pg-socket"
/usr/lib/postgresql/16/bin/initdb -D "$PWD/.work/reg-pg-data" -A trust
/usr/lib/postgresql/16/bin/pg_ctl -D "$PWD/.work/reg-pg-data" -l "$PWD/.work/reg-pg.log" -o "-h 127.0.0.1 -p 55449 -k $PWD/.work/reg-pg-socket" start
/usr/lib/postgresql/16/bin/createdb -h 127.0.0.1 -p 55449 registration_test_local
REGISTRATION_TEST_PG_URL=postgresql://$(whoami)@127.0.0.1:55449/registration_test_local node --experimental-strip-types --test server/test/registration-v2.test.ts
/usr/lib/postgresql/16/bin/pg_ctl -D "$PWD/.work/reg-pg-data" stop -m fast
rm -rf "$PWD/.work/reg-pg-data" "$PWD/.work/reg-pg-socket" "$PWD/.work/reg-pg.log"
```

Run from the worktree root with project dependencies installed and Node 22. The suite uses a unique schema and drops it in `finally`; it validates PG major version and the test URL, but the operator must ensure the instance is actually disposable. It uses only an in-memory mock email adapter. It covers migration rollback and uniqueness, no early account, sub/GC login and contact preservation, Unicode/bounded names, valid US phone formatting, rejected malformed/overlong/non-US numbers and extensions, no phone truncation, non-consumption on invalid input, missing-table and downstream profile rollback, new ownership, source non-linkage, denial of access by both owner and non-owner through the older consent service, disabled dependencies, denial/invalid role/spoofed fields, delivery failure and in-flight delivery, expiry/replay, legacy/v2 duplicates, and concurrency.
