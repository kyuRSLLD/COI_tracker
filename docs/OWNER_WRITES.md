# Owner-scoped manual writes — disconnected foundation

**Maintenance must remain enabled.** This is not a privacy remediation, route, migration runner, deployment change, or production data change. Nothing imports this service from startup or an HTTP route. Legacy routes and indirect access paths remain unsafe; see `OWNER_FOUNDATION.md` and `MAINTENANCE.md`. The v1 ownership migration and its unchanged source-table constraints are prerequisites. Apply it only under the separately documented approved offline process; this work does not apply it anywhere.

## Integration contract

`ownerWrites(connection, verifiedSubject)` offers `createSubcontractor`, `updateSubcontractor`, `createCoi`, and `updateCoi`. The service cannot authenticate a caller or prove that a string is verified. A future trusted server boundary **must** validate the signed credential, signature, issuer, audience, expiry and immutable subject using production-grade configuration, then pass only that verified subject. Never derive it from request body, query, path, client-supplied GC/owner ID, or JWT role alone. The existing authentication middleware and its development fallback have not been approved for this integration. Do not expose this service directly to untrusted clients. Review disabled/deleted-account semantics: the current users schema has no active flag.

Every operation checks the current DB role inside its transaction. Only `users.role = 'gc'` is accepted; admin is not an override. PostgreSQL locks that user's row until commit/rollback, and SQLite takes `BEGIN IMMEDIATE`, so a concurrent role change that commits first denies the write, while a write that locks first can finish before revocation. This is a transaction-order guarantee, not retroactive cancellation of already authorized work. Same-GC operations are serialized on PostgreSQL; plan for contention and configure appropriate server-side statement/lock/transaction timeouts. For PostgreSQL, use the usual READ COMMITTED isolation: stronger isolation can fail with serialization errors, which must fail closed. All other writers and administrative mapping changes must respect the same database constraints and locking model; direct privileged SQL, legacy services, and databases without enforcement can bypass the service. There is no RLS.

Each create uses a server-generated UUID and UTC timestamps, and creates the source row plus its exact explicit mapping atomically. A COI may only be created for a currently mapped owned subcontractor. Both updates include owner and live-role predicates in the mutation and lock the appropriate mapping(s); COI mappings must match both the actual COI parent and the owner's sub mapping. No global fallback or ownership inference exists, even for identical names/email or a legacy COI attached to an owned sub. No API changes or deletes a mapping, a source record, a parent relation, or dependent data. Out-of-band deletion of a mapping is possible with sufficient privileges, and must be handled separately by a reviewed access-revocation/retention design. The migration's foreign keys protect mapped source rows; they do not protect unmapped data from unrelated code.

Inputs are strict allowlists. Subcontractor create requires `company_name` and `trade`; optional nullable fields are `contact_person`, `phone`, `email`, `address`, `notes`. COI create requires `subcontractor_id`, `carrier`, `effective_date`, `expiration_date`; optional nullable fields are `am_best_rating`, `policy_number`, `reviewer_notes`. Patches accept only those data fields other than `subcontractor_id`; omitted fields stay unchanged and nullable fields may be cleared with `null`. Empty patches are invalid. Required strings are trimmed, nonempty and at most 500 characters; optional strings are at most 4,000 characters. Dates must be real `YYYY-MM-DD` calendar dates with effective date not later than expiration, including on partial updates. IDs are nonempty strings with maximum length 500. Status is always initially `pending_review`; review/status transitions, `user_id`, certificate fields, files, coverage, and associated records are intentionally outside this service. No contact or document verification, business-specific email/phone validation, auditing, rate limiting, or file handling is implemented. These require separate design before release.

Create/update returns only `{ id }` on success; missing, unmapped, foreign-owned, non-GC and unknown subjects all return `undefined`. The caller must preserve the indistinguishable outcome for unowned vs missing IDs and must not expose database/stack details. `OwnerWriteError` exposes only `INVALID_INPUT` or `STORAGE_FAILURE` and generic messages, without underlying errors or input data. Avoid logging raw inputs, SQL, credentials, or driver errors. An invalid request may be rejected before authorization. Treat any `STORAGE_FAILURE`, including BEGIN, COMMIT, or rollback failure, as an uncertain transaction outcome: discard the connection, investigate, and do not blindly retry. Reconciliation/idempotency for uncertain commits is not provided. A normal validation failure inside the transaction rolls back. The API intentionally returns no source record; any subsequent read must use an appropriate scoped service such as `ownerReads`.

Use an exclusive, dedicated, idle connection for the *entire call*: a checked-out PostgreSQL `PoolClient` or connected `Client`, never a pool; for SQLite use a dedicated database connection and enable `PRAGMA foreign_keys = ON` before use. The service checks SQLite foreign key enforcement on each call. SQLite must support `RETURNING` (3.35+), and each SQLite writer including other code must enforce foreign keys. Do not share a connection concurrently or call inside another transaction; lifecycle and disposal belong to the caller. No SQL values are interpolated; patch column names are compiled from static allowlists. There are no retries, nested transactions, or network/storage effects inside the service. Migrations are assumed to be correctly applied and undrifted; inspect actual production constraints separately.

Before enabling any functionality, replace and security-test **all** legacy unscoped routes and indirect project, portal, sharing, upload, email, stats, document and admin access; handle storage authorization separately; implement reconciliation for historical ownership only through a reviewed human-verified process; review actual deployed schema/constraints, principal grants, connection handling, timeouts and rollback; rehearse migration/restore on a sanitized clone; conduct independent security and privacy review and full integration/IDOR/concurrency tests. Maintenance remains on until all release gates in the existing documents are met.

## Local tests

From repository root: `node --experimental-strip-types --test server/test/owner-writes.test.ts`. The SQLite tests use a fresh temporary file and two dedicated connections and delete it afterward. PostgreSQL tests run only with `OWNER_WRITES_TEST_PG_URL` set to a **disposable loopback** database named `owner_foundation_test_*` without URL options; each fixture creates and drops a randomly named schema. Use a locally initialized disposable PostgreSQL 16 cluster, not production, a clone, or a shared database. See `server/test/owner-foundation.test.ts` for the separate existing migration/read suite and its `OWNER_FOUNDATION_TEST_PG_URL`. Tests cover current role, cross-tenant/unmapped IDs, strict fields and reparenting, parameterization, date checks, rollback including constraint and rollback failures, role-lock ordering, mapping contention, concurrent patches, and disabled SQLite FKs. Synthetic representative tables do not prove compatibility with the deployed schema, network/auth boundary, other writers, or full release security.
