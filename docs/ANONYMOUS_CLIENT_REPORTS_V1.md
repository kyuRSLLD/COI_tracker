# Anonymous client reports v1 — isolated, default off, not deployable

This is a disconnected prototype. Nothing imports it into `app.ts`, `secure-v2-app.ts`, startup, the legacy client, uploads, or an existing public/report/data route. There is no deployment or automatic migration. Only its independent migration is exercised alongside metadata 006 in the disposable combined test; its router remains unmounted and default-off. Keep maintenance enabled. `createAnonymousReportsV1Router()` returns only 404 and requires no dependencies unless an explicitly trusted composition sets `enabled: true`. The existing secure-v2 factory deliberately does **not** allow this route; integration requires a separately reviewed, exclusive application/ingress change, not mounting it next to legacy routes.

## Critical ownership and data blocker

Legacy `projects.user_id` and `project_subcontractors` do not constitute the reviewed, enforced ownership and membership association required here. No identity is inferred from them, names, email, or other legacy data. The new `report_v1_projects` is a **separate, initially empty, disabled** report-only namespace, not a mapping to a legacy project. It has an explicit GC owner foreign key and defaults disabled. There is no HTTP route here to create/enable a report project or populate its members, and there is no backfill, sync, or privileged production provisioning workflow. The tests insert synthetic rows directly. Consequently the API **cannot share actual existing projects** until a separately designed and reviewed provenance-backed ownership/membership association, authorized provisioning and status projector are built; it must not be activated on real data before that. Fabricating those associations would break the security model.

A future trusted projector must validate project ownership and every member-to-project association at the source, enforce consent/permissions as applicable, allocate the project and its owner atomically, omit `label` on insert so PostgreSQL's random UUID default generates it once per membership, persist it through status updates, and never accept labels or status prose from clients. The same source member in different projects gets independent randomly generated labels; do not copy labels between projects. Serialize membership changes with a project `FOR UPDATE` lock (reader holds project `FOR SHARE`), prevent source-ref reuse/reassignment, and use only the enum values specified below. Enforce column-level grants so the projector cannot insert or update `label`, and no untrusted actor can write these tables. A compromised/incorrect privileged projector or direct SQL can bypass these guarantees; CHECK constraints alone cannot verify randomness or actual ownership. A report project may initially be empty. There is no contact API, messaging, export, download, document, storage or certificate route.

## Minimal integration contract

Illustrative mount, **not a startup change**:

```ts
import { createAnonymousReportsV1Router } from './routes/anonymousReportsV1.ts'
// Mount only on an exclusive, reviewed v2 application after all blockers are resolved.
app.use('/api/v2/client-report', createAnonymousReportsV1Router({
  enabled: true, pool: reviewedPgPool, authenticate: reviewedCredentialVerifier,
}))
```

The verifier is trusted application code. It must verify the exact auth-v2 bearer JWT (signature, algorithm, issuer, audience, subject, time claims and JWT ID), reject missing/invalid/revoked credentials, and pin a frozen `req.securePrincipal = { subject, role, credential }` before `next()`, as in `GC_OWNER_V2_ROUTER.md`. Never derive subject from request fields. The owner actions recheck and lock the current `users.role = 'gc'`, verified enabled account and specific session, and recheck JWT/session expiry at transaction end using `withOwnerV2Transaction`. Non-GCs and missing/foreign report projects are denied; admin has no override. Creation requires an enabled project; revocation is also permitted for a disabled owned project. The live session/account checks are at creation and revocation, not an ongoing requirement that the creator's individual login remain open. A redeemed capability does require the owning user's current GC role and verified enabled account, and an enabled project. Restoring a disabled account/project or GC role can make an otherwise valid token usable again; revoke tokens explicitly for permanent invalidation.

All routes are POST with JSON, no query string, 8 KiB body limit and no-store/no-referrer headers. Authenticate only the owner operations; the redeem operation requires no account/cookies. Exactly these payloads are accepted (extra keys rejected):

* `POST /owner/create` (verified GC bearer): `{ "project_id": "<report-only UUID>", "scope": "anonymous-report:v1", "ttl_seconds": 3600 }`. TTL must be an integer from 60 to 604800 inclusive. A 201 response contains only `{token, scope, expires_at}`. This is a sensitive owner response; token is returned once and never recoverable from storage. Generate a fresh 256-bit random token and store only SHA-256 hash. The token is a transferable bearer capability, not client authentication. Use a short TTL and an independently secured delivery channel.
* `POST /owner/revoke` (same owning GC with current session): `{ "project_id": "<report-only UUID>", "scope": "anonymous-report:v1", "token": "<capability>" }`. Returns 204 on newly revoked token; foreign/missing/already revoked returns generic 404. A GC must retain the secret securely in order to revoke an individual token; no listing/recovery endpoint is provided. Project disable can stop all reads while disabled. Do not put capabilities in URL paths, queries, logs, analytics or referrers.
* `POST /redeem` (anonymous): `{ "token": "<capability>" }`. Returns exactly `{ "schema": "anonymous-report-v1", "members": [{ "label": "Member-<32 lowercase hex characters>", "status": "compliant|noncompliant|pending|unknown" }] }`. This example notation describes enum values; an actual status is one enum string. Only these primitive fields are selected and explicitly projected for each nested object, validated after DB read, and no `SELECT *` is used. Maximum 500 members; exceeding this fails closed with 503. An empty list is valid. Expired, revoked, unknown, foreign-scope, disabled-owner/account/project capabilities get the same generic 404. Malformed body yields 400, oversized body 413, wrong content type 415, infrastructure failure 503; no raw exception is returned.

The client gets no names, contact information, carrier, policy numbers, IDs, keys, documents, URLs, notes, free text or links. However, pseudonyms and status are **not a guarantee of anonymity**: GCs/clients may re-identify members from the project, status, population, timing or outside knowledge. Require privacy/legal review and evaluate whether even those fields should be shared.

## Fragment-only client flow

`server/examples/anonymous-report-viewer.html` and `anonymous-report-viewer.js` are **unmounted examples**, not a deployed page. After explicitly approved integration, the owner can privately deliver a link shaped `https://<reviewed-origin>/<viewer-path>#<token>`. A URI fragment is not included in the HTTP navigation request or normal referrer; the page reads it locally, immediately replaces browser history to remove it, and POSTs `{token}` to the fixed same-origin `/api/v2/client-report/redeem` endpoint with no cookies, no referrer, no cache and no redirects. The viewer uses `textContent` only. Test the actual browser, ingress and final deployed asset paths. Reload after the fragment is removed cannot recover the token; reopening the original link is necessary. The owner create response is **not** automatically sent to a client, and no email or client contact is implemented.

Fragments are visible to page JavaScript, browser extensions, the recipient, clipboard/history synchronization, screenshots and any system/channel used to send the link. They are not protection against malicious browser software or forwarding. Serve over HTTPS only; no third-party JS, analytics, pixels, error reporting, page instrumentation, redirects or service worker should see these assets or capabilities. Disable/correct existing service workers and browser extensions are outside server control. Apply a restrictive tested CSP (e.g. `default-src 'none'; script-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`), no-store and `Referrer-Policy: no-referrer` via HTTP response headers on viewer and API. Avoid all request/response body, token, auth header and full URL logging at app, proxy, tracing and error-monitoring layers; even discarded query strings can be logged before reaching Express. Refuse alternate origins/CORS and use a dedicated reviewed ingress. Viewer and API must be on the same origin, static asset paths reviewed, with no dependency on the legacy SPA. No CSRF cookie authentication is supported; if integration changes that, a separate CSRF/origin review is mandatory.

## Concurrency and database contract

Services use checked-out, exclusive PostgreSQL clients and READ COMMITTED transactions. Owner actions lock user, account, session, then project; token revoke updates the capability row. Redemption first performs an **untrusted discovery** by hash, then locks user, account, project and capability in that order and rechecks all authorization, scope, revocation and database-clock expiry after waits and immediately before COMMIT. If revocation commits before redemption acquires its capability lock, redemption fails; if redemption holds its shared capability lock first, revocation waits until the redemption transaction commits. Previously delivered or already-authorized/in-flight bytes cannot be recalled and a response can arrive after revocation commits. Expiry likewise is checked before commit, not guaranteed at receipt. Role/account changes and project disable serialize with the locks, subject to all writers honoring compatible lock discipline. Project content changes need a `FOR UPDATE` project lock to serialize with readers; no such production projector exists. Set finite pool, statement and lock timeouts. Failure/ambiguous COMMIT can mean an unknown write outcome: do not blindly retry; a possibly created but undisclosed token cannot be recovered and expires by TTL. Connections encountering errors are destroyed. No RLS, audit log, rate limit, abuse detection, pagination, revocation-by-ID, bulk revocation, retention or recovery is implemented.

## Manual migration and synthetic tests

`migrateAnonymousReportsV1(client)` is a manual PostgreSQL-only migration, invoked only on a dedicated idle client. It creates a separate migration ledger and tables in one transaction with an advisory lock; matching reruns are no-ops and unknown/changed history fails closed. It creates no project rows, changes no legacy model or data, and has no startup hook or rollback migration. Do not run on production or real data without a separately approved migration runner, schema/grants review, backup/restore rehearsal, offline deployment plan and security review. Do not edit a migration after it is applied. No migration is run by this work except against the disposable synthetic test cluster.

From the worktree with dependencies and PostgreSQL 16 locally installed:

```sh
scripts/test-anonymous-reports-v1.sh
node --experimental-strip-types --test server/test/anonymous-report-viewer.test.ts
```

The runner initializes and destroys a fresh loopback-only PostgreSQL cluster and random schema, with fake users, sessions, isolated projects and poison data; it never loads application or production config. The direct test requires `REPORT_TEST_PG_URL` naming a loopback-only `report_test_*` database without URL options. It exercises migration rerun, explicit default off, token hashing/scope/TTL, current session/account checks, cross-owner denial, independent pseudonyms, nested poison exclusion, expiry/revocation and actual queued revoke/read plus expiration while waiting on a row lock. Viewer unit tests check fragment removal before POST, no credentials or referrer, strict fields and text rendering; they do not prove browser, proxy, CSP, tracking or service-worker behavior. Release additionally requires independent privacy/security review, source provenance design, ingestion tests, auth and browser end-to-end tests, production schema/grants and migration/restore rehearsal, rate limiting and operational controls, and elimination of all unsafe legacy access paths.
