# Consent-based relationship prototype

**Do not merge, deploy, expose publicly, or use with real people, files, or customer data.** This is a development-only experiment. The existing application has globally scoped legacy COI/subcontractor endpoints and public local `/uploads` serving. Those paths are unchanged and can expose or change information independently of these new controls. Existing client-share routes are also outside this experiment. This prototype makes no new project or client-share links, but it cannot guarantee app-wide client privacy while the legacy endpoints remain unsafe.

## Scope and remaining product gaps

This backend implements real, separately stored relationship records in the synthetic test database, rather than the existing staged-only relationships. A GC may redeem a sub-issued QR *capability*, or a sub may explicitly accept a GC invite. A connected GC can read only the associated sub's current structured COI metadata and coverages through the new list endpoint; later COIs appear without copying them. A sub can revoke access. Relationship consent alone grants no certificate-file access. The separate, default-off synthetic-file experiment requires additional explicit consent; see [PRIVATE_CERTIFICATE_PROTOTYPE.md](PRIVATE_CERTIFICATE_PROTOTYPE.md). No feature handler modifies or deletes source COIs or coverage rows, adds project memberships, or returns certificate URLs or storage keys. Conservative filtering removes an entire metadata string that looks like a link, and may suppress harmless data; it is not a full data-loss-prevention system. A sensitive free-text field may contain encodings not detected by this filter. Do not treat this as production private file enforcement or use it on real data.

Development-only UI panels can render a subcontractor QR and scan it into a separately scoped test list. They require an additional explicit Vite development flag and are not available in production. GC invitation delivery is not integrated and no UI grants or retrieves certificate files. The earlier staged invitation and list screens do not use this relationship API. See the UI prototype README for test setup and remaining gaps. The sub may consent to any qualifying GC scanning the QR; the disclosure explicitly states this. It is not a GC-specific approval. GC invite acceptance is specifically bound to the previewed GC account ID and company name, which are rechecked on acceptance.

This is **not a production authorization model**. Existing legacy data has no trustworthy tenant ownership or business/email verification; a two-way, unique users-to-subcontractors association is required and rechecked on each operation, but unsafe legacy endpoints can manipulate underlying records. Existing credentials/registration, profiling, CORS, password flows, audit integrity, privacy, migrations, event notification, abuse/rate limiting, CSRF/browser threat review, metadata filtering, private storage, sharing, and secure file retrieval need independent design and review. A forged or shared bearer capability may be redeemed by anyone with the appropriate qualifying role. There are no rate limits; do not expose the prototype to an untrusted network. Only SQLite is supported; PostgreSQL behavior is deliberately not implemented or tested. There is no automated protection against someone deliberately placing real data in a `/tmp` database. Existing schema changes are not a production migration.

The all-current-and-future relationship scope means all structured metadata fields currently enumerated by the new API, except file locations and conservatively redacted link-like values. A future schema field will **not** automatically be added: update the reviewed allowlist, disclosure, and tests when fields change. This grant does not authorize file access. The separate synthetic file experiment is not production storage or an application-wide privacy control. The existing staged feature and its gates remain unchanged; its pairs grant no access here.

## Fail-closed gate

The new schema is created at startup only if the process boots with `RELATIONSHIP_PROTOTYPE_ENABLED=true`, `NODE_ENV=development` or `test`, no `DATABASE_URL`, and an explicit absolute `SQLITE_PATH` inside a real subdirectory of `/tmp`. Existing or dangling file symlinks are rejected. Routes additionally require an explicitly configured JWT signing secret at least 32 UTF-8 bytes, equal to the secret captured by the auth module and not its development fallback. Changes to the flag, mode, database URL, SQLite path, or signing secret after startup cause the API to return 503. Production always returns 503 and does not create prototype tables. These checks are safeguards against accidents, not a sandbox against a local adversary or a guarantee that a database contains only synthetic data.

## API contract

Base: `/api/relationship-prototype`. Every route requires an existing login JWT in `Authorization: Bearer ...`, validates the signed role and the current database role, and returns `Cache-Control: no-store`. Bodies are limited to 4 KiB. A valid GC needs a current `gc` user with nonblank company name and exactly one GC settings row owned by that user. A valid sub needs a current `sub` user with a nonblank account company and exactly one mutually associated profile; the profile must be referenced by only that user. Those conditions are rechecked on use and on every data read. Names are self-asserted, not verified identities. Profiles must be established explicitly in disposable test data; no email or name matching is performed.

1. `GET /disclosure` (sub): returns `{version, scope, qr, invitation}`. Display the full scope plus the correct flow-specific disclosure before collecting consent. Both flows require JSON `consent: true` and the exact `consent_version` from this response. Merely retrieving text or using a staged QR grants nothing.
2. `POST /gc-invitations` (GC): returns `{id, token, expires_at}` once. Token is 256-bit random, one-use, valid for 24 hours, persisted only as SHA-256. No email is sent. A sub calls `POST /gc-invitations/preview` with `{token}` to receive `gc_user_id`, `gc_company_name`, expiry and disclosure, then `POST /gc-invitations/accept` with `{token, gc_user_id, gc_company_name, consent: true, consent_version}`. The exact preview identity must still match when accepting. Expired, revoked, used, changed, or invalid capabilities return a generic 404.
3. `POST /sub-qr` (sub): send `{consent: true, consent_version}` after disclosure; returns one-use `{id, token, expires_at}` valid 10 minutes. The token itself is the QR payload, but no actual image or camera UI is provided here. A signed-in GC posts `{token}` to `/sub-qr/preview`, then `/sub-qr/accept`. The QR grants access to whichever qualifying GC first redeems it; no additional sub approval is performed. Connection and capability consumption are transactional.
4. `GET /gc/connections` (GC): returns only active, currently valid sub relationships owned by that GC and an allowlisted `cois` array with nested coverages. Missing or ambiguous identity associations fail closed. This endpoint is separate from `/api/subcontractors`, `/api/cois`, and the existing staged relationship list.
5. `GET /sub/connections` (sub): lists the sub's active GC relationships. `DELETE /sub/connections/:gcId` revokes the caller's own connection and invalidates all their outstanding unconsumed QR capabilities, preventing a previously issued QR from undoing revocation. A new connection requires a fresh affirmative consent. Revocation serializes with redemption and list reads in SQLite; an already returned response cannot be recalled.
6. `DELETE /capabilities/:id` revokes a capability owned by the authenticated actor. Revoking an already used capability does not revoke the connection; use the sub connection endpoint. Deleting one GC's invite or sub's QR does not affect another owner's capabilities.

Tokens are never passed as request paths or query parameters; use POST JSON bodies, TLS if ever transported, and no request-body logging or tracing. No attempt is made to secure other legacy application surfaces. Consent events record account IDs, profile ID, GC name snapshot, version, source and timestamps, but are not tamper-evident and have no deletion/retention policy. SQLite transactions serialize acceptance, revocation and scoped list reads. Connection revocation does not delete the underlying COI data.

## Tests and commands

From the worktree root with Node 22 and dependencies installed:

```sh
npm run test:relationships --workspace=server
npm run test:invitations --workspace=server
npm run build --workspace=server
```

The relationship test uses only ephemeral SQLite files under `/tmp`, synthetic identities, synthetic COIs and fake file URLs. It exercises both flows, current/future records, two GCs and two subs, identity and role rejection, unique source-profile checks, consent and preview binding, no URL/key fields, conservative link filtering, no source mutation by feature routes, no client grants, revocation, stale QR invalidation, token hashing/expiry/replay, racing QR redemption and revocation, rollback, and default-off/production/path gates. Existing invitation regression tests remain independent. Neither suite proves production security, private storage, UI behavior, nor PostgreSQL concurrency.
