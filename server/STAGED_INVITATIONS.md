# Staged GC invitations and subcontractor QR — NOT a production connection

This is an isolated experiment, not a shipped onboarding flow. It records an **intent/relationship in separate staging tables only**; it does not create an `upload_requests` row, attach a subcontractor to the legacy GC dashboard, grant access to COIs or certificates, or send email. The existing global subcontractor, COI, settings, upload and legacy join endpoints are **not made safe by this change**. Do not direct users to `/api/settings/qr-invite`, `/api/sub/join*`, or legacy `/join` as a replacement for this flow. Do not display `status: staged` as a completed COI connection.

At process startup the staging schema is created only if `STAGED_INVITES_ENABLED=true` and `NODE_ENV` is not `production`. All endpoints return 503 unless that flag is set, `NODE_ENV` is not `production`, and the actual JWT signing secret is configured explicitly, is not the old fallback, and is at least 32 UTF-8 bytes. Use a strong random secret. The flag must be set **before startup**; flipping it at runtime does not create schema. Do not enable this experiment against a production database or expose it publicly. No deployment is included.

## Contract

The authenticated endpoints use the existing `Authorization: Bearer <login JWT>` obtained from `/api/auth/login` or `/api/auth/register`. The middleware validates the JWT, then this feature checks both the JWT role and the user's current role in the database. Bodies are JSON. All feature responses set `Cache-Control: no-store`; valid requests also receive `Referrer-Policy: no-referrer`. Maximum JSON body size for this route is 4 KiB; malformed and oversized bodies return a generic 400/413 without logging the body by the app. All normal failure responses contain only `{ "error": "..." }`.

| Method and path | Auth and JSON body | Success |
|---|---|---|
| `POST /api/invitations` | GC; `{ "max_uses": 1 }`, optional `max_uses` integer 1–10, default 1 | 201 `{ "id": "...", "token": "...", "expires_at": "ISO UTC", "max_uses": 1 }`. Token returned **once**. Expires in 24 hours. |
| `POST /api/invitations/info` | Public; `{ "token": "..." }` | 200 `{ "gc_company_name": "...", "expires_at": "ISO UTC" }`. Invalid, expired, exhausted, revoked, or invalid owner → generic 404. |
| `POST /api/invitations/accept` | Signed-in `sub`; `{ "token": "..." }` | 200 `{ "status": "staged", "created": true }`. An existing pair yields `created: false` without consuming a use while the token is still valid. Otherwise unavailable token → generic 404. |
| `GET /api/invitations` | GC | 200 `{ "invitations": [{ "id", "created_at", "expires_at", "max_uses", "uses", "revoked_at" }] }`, only the caller's entries, no token/hash. |
| `GET /api/invitations/relationships` | GC | 200 `{ "relationships": [{ "sub_user_id", "created_at", "source" }] }`, only the caller's staged pairs. No contact, password or certificate data. |
| `DELETE /api/invitations/:id` | GC | 200 `{ "revoked": true }` for an owned ID (idempotent); unknown or another GC's ID → 404. Revocation prevents new uses; it does **not** remove previously staged pairs. |
| `POST /api/invitations/sub-qr` | Signed-in `sub`; `{ "trade": "Electrical" }` | 201 `{ "id", "token", "expires_at" }`. A fresh one-use token, returned once, expires in 10 minutes. `trade` is required, 1–120 characters after trimming, no control characters. |
| `POST /api/invitations/sub-qr/info` | Signed-in GC; `{ "token": "..." }` | 200 `{ "company_name", "trade" }` only; never consumes or creates a relationship. |
| `POST /api/invitations/sub-qr/accept` | Signed-in GC; `{ "token": "..." }` | 200 `{ "status": "staged", "created": true }`; even if the pair already exists (`created: false`), the QR is consumed. Invalid, expired, consumed, revoked, or invalid sub owner → generic 404. |
| `DELETE /api/invitations/sub-qr/:id` | Signed-in sub owner | 200 `{ "revoked": true }` for an owned ID (idempotent); unknown or another sub's ID → 404. Does not delete a pair. |

Missing/bad JWT → 401; wrong role or nonexistent user → 403; missing/ambiguous required owner/sub profile → 409; invalid `max_uses` or `trade` → 400. Public GC-invitation info/accept and sub-QR create/info/accept operations share one database-backed global rate budget (authenticated QR revocation is excluded) of 120 attempts per minute; over limit → 429. Rate-limit storage errors fail closed with 503. This crude global limit is susceptible to denial of service and is NOT a production abuse-control strategy. Configure trusted edge limits (global and per client), monitoring, bounded retention, and IP/proxy policy before considering production.

The token is a cryptographically random 32-byte (256-bit) base64url capability; only SHA-256 is persisted. The information/accept paths take it in a **POST body**, not the request URL. Invitation creation and responses must never be logged, cached, or recorded by tracing/analytics, proxies, browser history, error reporting or support tools. The opt-in development UI creates same-origin QR and email-draft links carrying the token in a URL fragment, removed when the landing page first loads; tokens are sent to APIs in POST bodies. It does not send email. QR/email share the same bearer capability: anyone who receives it can accept, so sharing must be deliberate and recipient-specific invitations should use one use. This is not an email-verified or recipient-bound invitation. Links are bearer capabilities; anyone receiving the link can use it. No real email service is invoked.

The GC must be a real existing database user with role `gc`, a nonempty `users.company_name`, and **exactly one** `gc_settings` record with `user_id` equal to that user's ID. The info name comes from the user's company name, not mutable global settings. Ownership is rechecked on lookup and acceptance; losing or duplicating the profile invalidates outstanding invites. This check establishes only a database association, **not verified control of a business, organization, email address, or a production tenant**. Existing GC registration/settings flows do not reliably provision such an owner profile; an isolated test/operator must establish one. Do not backfill it by guessing an email, `LIMIT 1`, or company name.

For acceptance of a GC-generated invitation, the authenticated sub must be a currently valid `sub` database user whose `users.subcontractor_id` points to a subcontractor row with the same `user_id`. For sub-generated QR, identity is instead the existing authenticated, current-role `users` account itself, and the QR endpoints never read or write the global `subcontractors` table. The sub must intentionally supply the trade to share; it is a self-asserted snapshot, not the stored trade and not independently verified. The shared company is the trimmed `users.company_name`, snapshot at issuance and rechecked on preview/accept; a current role or company mismatch makes a token unavailable. A nonempty account company is required. The scanning GC must be a current `gc` database user with a nonempty account company and exactly one owned `gc_settings` profile; this is checked on both preview and acceptance. No endpoint authenticates by body email/password or matches by email. Sign-in/registration happens separately through existing auth; new endpoint responses never expose `password_hash`. Current registration does not verify email ownership. Existing legacy APIs have unrelated serious access-control and account-linking flaws, so integration must address those first.

## Storage and atomicity

* `staged_gc_invitations`: owner ID and explicit settings ID; SHA-256 token hash (unique); created/expiry; bounded uses; revoked timestamp.
* `staged_sub_qr_capabilities`: sub user ID, self-asserted trade, account company snapshot, token hash, created/expiry, consumed and revoked timestamps. No raw token is stored. There is no listing endpoint; retain the returned ID to revoke.
* `staged_gc_sub_relationships`: `gc_user_id`, `sub_user_id` composite primary key, `created_at`, `source` (`gc_invite` or `sub_qr`), and `source_id`. The source ID is polymorphic rather than a database FK, so future integration must enforce and audit provenance. Pair identity is users, not global legacy `subcontractors` rows. The table grants no access to documents.
* `staged_invite_rate_limit`: shared global counter. It stores neither tokens nor client identifiers.

Acceptance locks the capability row on PostgreSQL and uses `BEGIN IMMEDIATE` on a dedicated SQLite connection. Within one transaction it validates owner/sub and token and inserts the unique pair with `ON CONFLICT DO NOTHING`. A GC invitation increments uses only if the pair was inserted. A sub QR consumes its one use even when the pair already exists; if the pair exists, the original provenance is preserved. Expiry is checked again after a potentially blocking pair insertion; failures roll back all writes. Revocation updates the same capability row and serializes with acceptance. PostgreSQL implementation has not yet been integration-tested, and concurrent ownership/profile provisioning needs database constraints and further design.

## QR client and consent limitations

Do not equate `/sub/public/:id` with an invitation capability. The opt-in development UI includes a QR image, camera scanner, and confirmation screen, but creates no production relationship. The authenticated sub explicitly requests a capability and supplies the shared trade; the scanner can preview before a separate confirmation request. This token is a bearer capability, **not bound to a specific GC**, and anyone with it and a qualifying GC account may consume it. Issuance is not consent to connect to an identified GC. Before production, add an independently verified, GC-specific sub consent step, provenance auditing and robust abuse controls. The prototype includes tokens in URL fragments for sharing and temporarily uses sessionStorage for login handoff; same-origin scripts and recipients may access them. Production requires a threat review and a tighter token lifecycle. QR creation controls lose revocation IDs on reload; the GC revoke API is not yet surfaced in the UI. Directly opening a sub-QR link does not perform scanning. Never place tokens in server request URLs, logs, analytics, or error reports. Consent to a staged relationship does not grant COI/document access; that requires a separately designed owner-scoped authorization and sharing model.

## Verification and outstanding work

Run `npm run test:invitations --workspace=server` (Node 22). It uses disposable SQLite databases and synthetic accounts, exercises multiple GCs and subs, owner isolation, authentication and role checks, profile ownership, expiry/revocation, concurrent redemption and revocation, replay, cross-flow pair uniqueness, no raw token persistence, rollback, rate limit, parser handling, and disabled/production gating. QR tests rename the legacy subcontractor table to prove the QR endpoints do not access it. It performs no real email or account access. PostgreSQL integration/concurrency, multi-process abuse behavior, production migrations, actual tenant ownership, external business/email verification, audited account/profile provisioning, registration within the invite flow, durable revocation controls, secure distribution, CSRF/token handling, existing global endpoint authorization and a separately designed COI-sharing model remain blockers to a production feature.

## Local integration test

`python3 client/tests/test_staged_integration.py` runs the UI and API with a disposable SQLite database, synthetic accounts and no real email. The development UI requires both Vite development mode and `VITE_STAGED_INVITES_ENABLED=true`. Never use production database credentials with these flags; they do not prove that a database is safe. Existing legacy APIs remain unsafe for real customer data.
