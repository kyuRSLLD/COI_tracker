# Private certificate storage — disconnected prototype

## Status and scope

`server/src/services/privateCertificateStorage.ts` is a production-intended building block, **not a deployed or integrated privacy fix**. No route imports it; no environment variable enables it; maintenance remains on. The opt-in factory and the injectable constructor both reject use unless `enabled: true` is explicitly passed by trusted server code. Neither has a local-disk, public-URL, presigned-URL, or other fallback. The factory creates the AWS SDK S3 client against an explicit HTTPS commercial regional S3 endpoint and uses the normal AWS credential provider chain. Only dotless DNS bucket names and commercial-region endpoints are supported; China, GovCloud, S3-compatible services, access point ARNs and custom endpoints need a separate reviewed implementation. No AWS calls were made in development or testing.

**The legacy `services/storage.ts` and existing routes are unchanged and unsafe to expose as a substitute:** they can use local static `/uploads`, direct/public-looking URLs, presigned URLs and fallback behavior. Keeping maintenance enabled is essential. This new module does not secure existing buckets, URLs, local files, routes, data or previously shared content. Do not turn maintenance off just because these isolated tests pass.

## Service contract

* A caller must obtain `MemberPrincipal` from verified server-side authentication, not from a body, query, header, or share token. The service refuses non-member/client principals. The callback is mandatory, invoked for every upload/download, and must return exactly `true`; errors and all other values deny. The callback must consult authoritative, current data and decide both action and exact certificate for the authenticated identity. It must enforce tenant ownership, status, scope and explicit active subcontractor consent to the particular GC (and project/document if consent is scoped that way). Unauthenticated, expired, revoked, cross-tenant, unconsented and client principals must fail closed. Tests use a toy consent callback, not a production policy.
* `certificateId` is an application-level identifier, **not an S3 key**. Only server-generated cryptographically random 256-bit keys under `private-certificates/` are used for S3. The repository maps an authorized certificate ID to a private key and verified MIME/size. The repository must be trusted server-side, scoped/unique across tenants, and must never accept client-provided keys. `create` must atomically insert only if the ID is absent; records are immutable. A replacement needs a new certificate ID/version and a separately authorized policy. `get` must return the authoritative mapping. Do not expose the key or metadata record to any API response or log.
* Upload authorizes before reading the stream, checks size and signatures, writes S3 with SSE-S3 (`AES256`) and no ACL, and then creates the metadata record. Only MIME/size are returned. This is **not a transaction**: an S3 success followed by a DB failure or ambiguous timeout can leave an orphan. Likewise a response can be lost after a write. Do not immediately delete on a failed metadata create: the DB commit may have succeeded despite an error. Design idempotency, transactional state, audit and a delayed, race-safe reconciliation/retention process before integration, accounting for in-flight writes and versioning. Never blindly remove objects based solely on a momentary missing row.
* Download first authorizes, then resolves the trusted mapping and returns a Node readable stream and defensive attachment headers. The route must stream the body through the backend, apply all returned headers unchanged, prevent intermediaries from caching, and terminate the response if the source errors or its actual length is incorrect. Never replace the stream with a direct S3 link, redirect, object key, signed URL, or legacy URL. If the client disconnects, destroy the returned stream to release the upstream response. Convert exceptions to generic responses; do not disclose bucket names, keys, AWS errors, cross-tenant existence or authorization details. Repository misses and storage failures are generic storage errors; map external status codes consistently with the application's anti-enumeration policy.
* The class accepts an injected transport to permit mock-only testing; production integration must use the factory, not an untrusted transport or a fake/local adapter. The service does not start an HTTP server or persist data itself.

## File and resource limits

Maximum accepted payload is **10 MiB (10,485,760 bytes)**, including an exact boundary. Allowed declared MIME values are exactly `application/pdf`, `image/jpeg`, `image/png`, and `image/webp`; they must match the initial file signature. There is no filename input, and the download attachment filename is a fixed safe name based on detected type. Empty, oversized, mismatched, unsupported, unreadable or unrecognized files are rejected before S3 writes. Uploads are buffered in memory after authorization, not sent as multipart uploads, and temporary copies mean per-request memory can exceed 10 MiB. Downloads are streamed and enforce the trusted stored size.

Signatures are **not complete parsing, malware detection, PDF sanitization, content disarm, decompression-bomb protection, or proof that a file is safe**. Polyglot files and malformed documents can pass. Before enabling, establish scanning/quarantine and safe document processing, validate full formats as appropriate, avoid opening documents in privileged processes, and rate-limit concurrent uploads and downloads. Configure reverse proxy, HTTP body and multipart parser size/time limits at or below the service limit, plus per-user rate, bandwidth and concurrency limits. Authenticate/authorize before buffering or accepting large bodies; handle rejected or disconnected request streams safely. Configure response security headers and disable unsafe previews; the fixed attachment, `nosniff`, and `private, no-store` are defense in depth, not content sanitization.

## AWS setup and least privilege (future work, not performed)

Create a dedicated private bucket in the selected commercial region; enable account- and bucket-level S3 Block Public Access, S3 Object Ownership bucket-owner-enforced (ACLs disabled), encryption at rest and TLS-only access. Lock down all other IAM principals, bucket policies, access points, CDNs and cross-account grants; do not use static website hosting or allow anonymous access. The module sends no `ACL` and requests SSE-S3 `AES256`. A bucket policy requiring SSE-KMS instead would reject these writes; KMS support and least-privilege key policy would need a reviewed change. Ensure workload credentials come from a short-lived execution role, not application/client secrets. For the service role grant only `s3:PutObject` and `s3:GetObject` on `arn:aws:s3:::YOUR-PRIVATE-BUCKET/private-certificates/*`, as needed; do not grant bucket public access controls, ACL changes, broad bucket/account administration or listing. Enforce secure transport with an appropriate bucket policy. Restrict roles/network as feasible, keep audit logs private, configure retention/backups and monitor access. An independent role/process may need narrowly scoped listing/deletion for approved, safe orphan cleanup. Versioned buckets, replicas and backups need their own deletion and retention plan. Validate effective policies and actual anonymity/access behavior in an isolated AWS test account before rollout; this code cannot guarantee account configuration.

## Revocation and remaining integration requirements

The module authorizes at the beginning of each operation. Revocation affects **later** requests if the callback reads current grants, but cannot recall bytes already delivered or reliably stop an in-flight stream. An authorization decision can also race revocation before the S3 read or metadata commit. If stronger guarantees are required, design grant versioning/locking, stream cancellation and a consistent policy store; even these cannot recall previously received copies, screenshots, backups or external caches. No URL expiration or key secrecy substitutes for consent authorization.

Before any deployment, separately design and review:

1. Authenticated user/tenant identity, project/subcontractor relations, explicit consent creation, scope, expiration, revocation and audit records; authorization must not depend only on a GC-sub relationship or possession of an ID. Define who can upload and whether consent is required for each upload. Use authoritative, current checks for every download.
2. A real immutable metadata repository with uniqueness/tenant controls, lifecycle/idempotency/cleanup, migrations and failure recovery. Treat its keys as server-only. This prototype makes no DB changes.
3. Backend-only upload/download endpoints with parser limits, streaming cancellation and generic errors; comprehensive cross-tenant, anonymous, client, revoked/expired consent, race, malformed file, proxy-cache and real S3 integration tests in an isolated environment. Do not accidentally import the legacy helper in the new path.
4. Client-view **data redaction**, separately from storage: clients must not receive subcontractor contacts, raw COIs, private object keys, direct document URLs, or other non-approved fields. The storage service blocks client principals but does not inspect or redact API payloads. Define an explicit allowlist and test all client-facing endpoints. GC access must be limited to consented subcontractor documents.
5. Inventory and privately migrate existing local/S3 objects and metadata; revoke public access, old signed/direct URLs where feasible, independent CDN/static paths, copies and credentials as appropriate. Already downloaded/cached copies cannot be recalled. A migration must account for old application instances and rollback.
6. Conduct a full security/privacy review of all endpoints and deployment infrastructure, scan documents, provision and verify the AWS account and policies, and complete release review before modifying production data, switching off maintenance, or deploying these disconnected components.

## Isolated verification

From the repository root, run `npm run test:private-storage --workspace=server`. Tests use synthetic data and a fake in-memory S3 transport and metadata repository, never a database or a real S3 request; an SDK client is only constructed to check valid factory configuration. They cover opt-in and invalid configuration; explicit authorization, GC consent revocation and client denial; random keys and no ACL; four signatures, mismatch, errors and the byte boundary; metadata and S3 failures; and safe streaming/cancellation. They do not validate real AWS policy, application-wide authorization/redaction, full file safety, concurrent revocation or the legacy routes.
