# GC granted-file viewer: unmounted prototype

`client/src/v2/GcGrantedFiles.tsx` exports `GcGrantedFiles`. It is included in the GC navigation of `V2Shell`, but that shell is **not mounted** in the application. The shell provides the current in-memory auth-v2 GC token only after `/me` verification, removes the viewer on navigation, sign-out, expiry or failed verification, and uses the session generation to force a remount on session change. Any other host must provide a current auth-v2 GC bearer token in memory as `authorizationToken`, clear it on sign-out and replace it on every session/account change, and unmount the component when appropriate. If the effective session can change without the token changing, the host must also force an unmount/remount. The optional `maxFileBytes` is a trusted lower deployment limit, never greater than 10 MiB. This interface does not establish the user's identity or authorization; the server remains authoritative.

The component calls only the fixed same-origin `/api/v2/self-reported-private-files/granted/list` and `/granted/:fileId` routes. Pagination is a POST containing `{after}`; no query strings or direct storage URLs are used. It lists only files returned by that API, without trying to infer an owner, company, insurance status, or access from metadata or connection state. The last listing is not a live authorization guarantee, and pagination is not a snapshot. Every open obtains a new authenticated response; a failure clears the old listing. There is no revocation notification, so already displayed bytes may remain visible until the user closes them or the session changes; delivered bytes cannot be recalled. Reloading the list cannot undo delivery. No files are persisted by this UI.

A preview is limited to the validated listed byte size and configured maximum, with a 30-second deadline, content-type/length checks and cancellation. Temporary blob URLs are revoked on close, refresh, session change and unmount. PDFs use an empty-sandbox iframe; some browsers may not display PDFs under that restriction. Sandboxing and scanning do not prove a document safe, verify insurance, or verify the uploader's identity or authority. Production integration needs independent security review, a restrictive CSP compatible with blob previews and a reviewed browser PDF policy. The backend router is opt-in only in the synthetic and separate unmounted production-intended compositions, not wired into startup; this component does not change that. There is no client-report access path in these compositions.

After installing workspace dependencies (`npm ci`), Python Playwright and Chromium, run from the repository root:

```sh
python3 client/tests/v2-gc-granted-files/test_gc_granted_files.py
./node_modules/.bin/tsc -p client/tsconfig.json --noEmit
(cd client && ../node_modules/.bin/vite build --config tests/v2-gc-granted-files/vite.config.ts --outDir /tmp/coi-gc-granted-files-build --emptyOutDir)
```

`CHROME_BIN` can select Chromium. The browser tests run an isolated local Vite host, intercept all API calls, block external network requests, and use only synthetic data. They cover empty permissions, separately granted files, pagination, revoke/download failure, invalid and oversized responses, deadline and stale ignored-abort responses, session switching and sign-out, object-URL cleanup, sandboxed PDF/image previews, focus/back/Escape, and mobile layout. They do not test real authorization, storage, malware scanning, browser PDF sandbox internals, production CSP, or deployment readiness.
